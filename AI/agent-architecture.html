如何设计一个 Agent：八种架构与组合路径 ​

「Agent 是什么」见：Agent 概念。本文回答另一件事：上手设计时，面前这八种架构该怎么理解、怎么选、怎么组。

很多人会把 ReAct、RAG、Multi-Agent 当成互斥选项。更稳妥的看法是：它们是可组合的设计模式——有的管「怎么想」，有的管「能调用什么」，有的管「怎样跑起来」。先建立地图，再谈组合。

不是八选一，而是三层组合 ​

把八种模式塞进一个运行时，会更清楚：

层回答的问题常见模式
Decision（决策）下一步怎么定？ReAct、Plan-and-Execute、Reflection
Capability（能力）任务靠什么能力完成？Tools、Memory、RAG
Runtime（运行）协作与持续跑到什么程度？Multi-Agent、Autonomous Loop
Guardrails（护栏）边界在哪里？权限、预算、终止条件、审计

公式可以记成：

Practical Agent = Model + Patterns + Guardrails

实用型智能体 = 模型 + 模式 + 约束机制

起步建议永远是：先用 ReAct + Tools 跑通最小闭环，再按业务缺口逐层加复杂度。

下面按层展开八种模式；读完再看「如何组合成真实产品」。

Decision（决策）：系统怎样思考和调整 ​

1. ReAct（推理与行动）：边做边判断 ​

ReAct（Reason + Act，推理与行动）是最常见的单 Agent 循环：根据目标与当前状态选一步行动 → 调用工具 → 观察结果 → 再决策，直到完成、触达预算，或请求人工。

  • 适合：开放研究、排障、路径事先说不清的动态任务
  • 风险：死循环、重复调工具、把错误观察当真继续推演
  • 一句话：走一步、看结果、再决定下一步；停止条件和状态记录必须写死

和概念文里的「思考 → 行动 → 观察」是同一套骨架，只是工程上要把 Observation（观察结果）规范化、把 STOP（停止）规则显式化。

2. Plan-and-Execute（规划与执行）：先拆解，再执行 ​

目标一上来就很长、依赖很强时，边想边做容易丢全局。Plan-and-Execute（规划与执行分离）先让 Planner（规划器）生成带依赖的任务图与完成条件，再让 Executor（执行器）一次只推进当前节点；走不通则 BLOCKED → REPLAN（阻塞 → 重规划）。

  • 适合：研报、开发交付、项目规划等长链路任务
  • 风险：初版计划脱离现实；环境已变仍机械执行旧图
  • 一句话：先画路线，再按依赖推进；走不通就重画

Planner（规划器）管「怎么拆」，Executor（执行器）管「怎么做」；接口是任务状态与重规划，而不是把一切塞进同一次推理。

3. Reflective Agent（反思型智能体）：用反馈闭环提质量 ​

Reflection（反思）把「生成」和「评价」拆开：先出草稿，再按明确标准（事实、完整、格式、引用等）打分；不达标就把反馈写进下一轮，并保留修订记忆避免重复犯错。必须设 满分阈值 与 最大轮数。

  • 适合：代码审查、报告、方案、文案等「有可定义交付标准」的产物
  • 风险：模型自评有共同盲区；无限反思烧钱却不更正
  • 一句话：按标准找问题，再把反馈变成下一版的输入

注意：多想几轮 ≠ Reflection（反思）。关键是有 rubric（评分尺） 和可执行的修改指令。

Capability（能力）：系统能访问哪些能力 ​

4. Tool-Augmented（工具增强）：从会说到会做 ​

模型负责表达「要调什么、参数是什么」；Tool Gateway（工具网关）负责校验、鉴权、路由、重试；工具返回规范化 Observation（观察结果：状态 / 数据 / 错误 / 审计）再喂回模型。发送、删除、支付等高副作用操作应走人审。

  • 适合：搜索、查数、办公自动化、接企业内部系统
  • 风险：参数错误、越权、重复提交、盲信工具返回内容
  • 一句话：模型提出行动，受控运行时真正执行

工程上这层常和 MCP / Function Calling（函数调用）相遇：协议解决「怎么接」，Gateway（网关）解决「接了以后怎么控」。更多见：MCP。

5. Memory-Augmented（记忆增强）：让状态跨轮次延续 ​

记忆不是无限聊天记录，而是选择性写入、整理、召回、遗忘。当前轮进入有限的 Working Memory（工作记忆）；Memory Manager（记忆管理器）决定沉淀到情景记忆（做过什么）、语义记忆（长期事实）、画像（偏好规则），并受相关性、时效、用户同意、可删除、可追溯等策略约束。

  • 适合：长期助手、跨会话项目、个性化服务
  • 风险：假记忆、过期信息、隐私泄露、无关历史污染当前决策
  • 一句话：记住有价值的经验，也要有能力忘记

和「知识库 / RAG」的分工：Memory（记忆）偏用户与任务状态；RAG 偏外部可检索知识。入门见：知识库。

6. RAG Agent（检索增强智能体）：主动寻找可验证证据 ​

RAG（Retrieval-Augmented Generation，检索增强生成）。生产级 RAG Agent 很少「检索一次就答」。更常见的是：查询规划与改写 → 多源检索（向量 / Web / SQL·Graph）→ 重排压缩成证据包 → 带引用作答 → Verifier（校验器）发现冲突或不足则回到规划再搜。

  • 适合：企业知识问答、研究分析、要实时事实的客服
  • 风险：召回失误、过期材料污染、引用错配、权限过滤失败
  • 一句话：先找到可信依据，再让模型组织答案

Runtime（运行时）：系统怎样协作和持续运行 ​

7. Multi-Agent（多智能体）：用角色分工放大能力 ​

多个专业角色共享目标、职责不同；Supervisor（主管）负责拆分、分派、汇总，处理冲突与终止；中间产物进 Shared Workspace（共享工作区 / 黑板 / 消息总线）。价值来自分工是否有效，不来自 Agent 数量。

  • 适合：可并行拆分、或需要多视角互审的复杂任务
  • 风险：通信成本高、上下文冲突、重复劳动、Supervisor 成为瓶颈
  • 一句话：有效分工，而不是堆角色

常见误区：任务还没跑通单 Agent，就上多人协作——协调成本会先把收益吃掉。

8. Autonomous Loop（自主循环）：从一次任务到持续目标 ​

把高层目标存成持久 Goal + State（目标 + 状态），按事件或定时驱动 Observe → Decide → Act → Evaluate（观察 → 决策 → 行动 → 评估），直到完成、暂停或升级人工。自主性越高，Guardrails（护栏：权限、预算、最大循环、审计、人批）必须越强。

  • 适合：持续监控、周期研究、运维响应、长项目推进
  • 风险：错误目标被放大、成本失控、未授权副作用、停不下来
  • 一句话：自主性越高，停止机制和治理必须越强

如何组合成真实产品 ​

八种模式讲完，设计问题变成：按任务复杂度，该叠哪几层？

安全叠加路径 ​

建议顺序：

  1. 需要对外行动 → Tools + ReAct（工具 + 推理行动，最小闭环）
  2. 需要私有/实时事实 → RAG（检索增强）；需要跨会话体验 → Memory（记忆）
  3. 长链路强依赖 → Planning（规划）；交付质量敏感 → Reflection（反思）
  4. 真要专业分工或持续运行 → 再上 Multi-Agent（多智能体） / Autonomous Loop（自主循环）

每加一层能力，同步加：评估、成本控制、权限治理。

参考流：竞品简报 Agent ​

真实产品很少只用一种模式。下面是一张「可控工作系统」参考骨架——持续生成竞品简报：

读法：

  • Plan + Supervisor（规划 + 主管）：管任务图、依赖、角色与预算（Plan-and-Execute + Multi-Agent）
  • Researcher / Analyst / Writer（研究员 / 分析师 / 写手）：各自跑 ReAct，分别挂 Tools / RAG / Memory
  • Reflection（反思）：事实审查、质量评分、不达标打回
  • 底座：定时触发、预算、权限、检查点、人工审批、审计（Autonomous Runtime 自主运行时 + Guardrails 护栏）

成熟 Agent 的标准不是「最自主」，而是：在明确边界内稳定完成目标——可组合、可观测、可治理。每条自动化路径都要能被看见、被评估、被停下来。

设计清单（可直接照着填） ​

  1. 边界：目标、成功标准、禁止事项、预算与人审点
  2. 最小闭环：单 Agent + ReAct（推理行动）+ Tool Gateway（工具网关）+ 停止条件
  3. 按缺口加层：缺知识加 RAG（检索增强），缺连续加 Memory（记忆），链路长加 Plan（规划），质量不稳加 Reflection（反思）
  4. 最后才扩 Runtime（运行时）：分工不动再 Multi-Agent（多智能体）；要持续跑再 Autonomous Loop（自主循环），并加强治理
  5. 验收：关键路径有日志、有评估、有熔断

能力演进的另一条叙述（Prompt → Context → Harness → Loop → Graph）见：从 Prompt 到 Graph。

小结 ​

  • 八种架构是模式库，不是互斥菜单
  • Decision（决策）管思考，Capability（能力）管手脚与知识，Runtime（运行）管协作与持续，Guardrails（护栏）管边界
  • 设计顺序：ReAct + Tools（推理行动 + 工具）最小闭环 → 按业务缺口叠加 → 同步加强治理
  • 产品形态用「目标 + 编排 + 角色循环 + 反思 + 运行时护栏」组装，而不是堆更多模型调用

概念与 Skill / MCP 分工仍以 Agent 概念 为准；接外部系统见 MCP，知识侧见 知识库。
