如何编写 Skill ​

概念与什么时候该封装，见：Skill 技能文件详细说明。本文只讲一件事：怎么把一个 Skill 写好。

写 Skill，不是写给同事看的说明文档，而是写给 Agent 执行的「操作协议」。写完后 Agent 应该能：知道何时启用、按固定步骤做、产出约定格式、不越界。

先想清楚再写 ​

动笔前只问四件事（答不清就先别建目录）：

问题写进 Skill 的对应位置
解决什么任务？边界在哪？标题 + 适用 / 不适用
什么话、什么场景该触发？description + 触发词
Agent 默认不知道什么？正文步骤、约束、领域知识
交付物长什么样？输出模板 / 示例

不建议封装：一次性任务、流程还在变、只是知识点不是执行流程。这些留给普通文档即可。

最小可行结构 ​

一个 Skill = 一个目录 + 一个入口文件：

text
my-skill/
├── SKILL.md          # 必填：主入口
├── references/       # 可选：长资料，按需再读
├── examples/         # 可选：输入输出样例
└── scripts/          # 可选：固定脚本

个人用可放本机 Skills 目录；要跟仓库走就放项目里的 .cursor/skills/（或团队约定的 skills 目录）。主文件始终叫 SKILL.md。

SKILL.md 骨架 ​

md
---
name: my-skill
description: （做什么）。（什么时候用）。
---

# 技能名

## 适用场景
- ...

## 不适用场景
- ...

## 执行流程
1. ...
2. ...

## 输出规范
...

## 验证清单
- [ ] ...

头信息里至少要有：

字段作用
name标识，小写 + 连字符，例如 code-review
description最关键：Agent 靠它决定要不要加载这个 Skill

正文章节名可以按任务调整，但尽量覆盖：何时用 / 何时不用 / 怎么做 / 交什么 / 怎样算完成。

写好 description（决定能不能被用上） ​

description 会被用来做技能发现。写糊了，等于 Skill 不存在。

规则 ​

  1. 第三人称陈述能力，不要「我可以」「你可以」
  2. 同时写清「做什么」和「何时用」
  3. 带上用户常说的触发词（评审、超时、发布、提交信息……）

对比 ​

yaml
# 差：太虚，没有触发信号
description: 帮忙处理文档相关事务

# 好：能力 + 场景 + 触发词
description: 从 PDF 提取文本与表格、填写表单、合并文档。在处理 PDF，或用户提到 PDF、表单、文档抽取时使用。

再举几条可直接套用的写法：

yaml
description: 按团队规范审查代码的质量、安全与可维护性。在评审合并请求、查看代码改动，或用户要求代码评审时使用。

description: 分析 git diff 并生成清晰的提交说明。在写 commit message、检查已暂存变更时使用。

description: 按固定步骤排查接口超时与线上报错。在用户反馈超时、5xx、白屏或要求排障时使用。

正文怎么写 ​

1. 只写 Agent 不知道的 ​

默认 Agent 已经懂通用编程与工具用法。Skill 里只补：

  • 你们团队的顺序与禁区
  • 固定命令、路径、环境
  • 输出必须长什么样
  • 失败时怎么回退

少写背景科普，多写可执行步骤。

md
# 差：先解释概念再绕到做法
PDF 是一种常见文档格式，市面上有很多解析库……

# 好：直接给默认做法
用 pdfplumber 提取文本；扫描件再走 OCR。

2. 步骤可执行，禁止「适当处理」 ​

每一步最好能回答：做什么、用什么、结果怎么判断。

md
## 执行流程
1. 收集：时间、环境、版本、复现路径
2. 定位：看错误率、延迟、关联 trace
3. 定级：单用户 / 局部 / 全量
4. 输出：临时止血方案 + 根因修复方案
5. 验收：按下方清单勾选

3. 先约束，再赋能 ​

「不能做什么」往往比「可以做什么」更能稳住 Agent：

  • 禁止跳过验证
  • 禁止未确认就发布 / 删数据
  • 禁止改动范围外的文件

4. 主文件宜短，细节旁路 ​

SKILL.md 建议控制在可读的短篇幅（经验上几百行内）。长规范、大表、完整 API 放到 references/，在主文件里只链一层：

md
## 更多资料
- 编码规范详见 [references/standards.md](references/standards.md)
- 成功 / 失败样例见 [examples/](examples/)

5. 自由度与任务匹配 ​

任务特点写法
多种合理解、看上下文原则 + 清单即可
有偏好格式、允许小幅变化给模板
必须一致（迁移、发布、对账）固定脚本 + 校验命令

五种常用写法 ​

按任务选一种主模式即可，不必堆满。

模板：锁死交付格式 ​

适合报告、纪要、评审意见。

md
## 输出规范

# [标题]

## 摘要
（一两句）

## 关键发现
- 发现 + 依据

## 建议
1. 可执行建议

示例：用样例对齐风格 ​

适合提交信息、文案、注释语气。

md
## 示例

输入：新增基于 JWT 的用户认证
输出：
feat(auth): 实现基于 JWT 的认证

新增登录接口与令牌校验中间件

清单：多步骤流程 ​

适合排障、发布、填表。

md
## 任务进度
- [ ] 收集上下文
- [ ] 定位信号
- [ ] 给出方案
- [ ] 验证通过

分支：写专家决策树，不是写流程说明 ​

适合「新建 / 编辑」「线上 / 预发」，以及评审、排障里「什么情况必须怎样」的判断。Skill 最值钱的往往不是步骤列表，而是熟手才会做的条件分支。

md
1. 新建内容？→ 走新建流程
2. 编辑已有？→ 走编辑流程

当改动涉及数据库时：
- 必须检查注入风险、事务、索引；不得默认全表扫描可接受

当 diff 过大时：
- 必须先要求拆分，再评审；不得对超大 diff 直接给合并结论

当发现安全或数据泄露风险时：
- 必须标成「必须修」；不得给出「可以合并」

闭环：改完立刻验 ​

适合文档生成、批量改写、任何「错了代价大」的任务。

md
1. 完成修改
2. 运行：`python scripts/validate.py output/`
3. 失败则修复后再验
4. 通过后才进入下一步

要不要加脚本 ​

下列情况优先写脚本，而不是让 Agent 每次现场拼命令：

  • 步骤固定、容易写错
  • 需要同一套校验反复跑
  • 想省上下文（脚本在仓库里，不必把实现贴进 Skill）

在 SKILL.md 里写清：脚本干什么、怎么调用、成功 / 失败长什么样。默认是让 Agent 执行脚本，而不是把脚本当说明书读完再重写一遍。

常见踩坑 ​

踩坑更好的做法
名字叫 helper / utils用动作名：debug-api-timeout、pre-release-check
description 只有「帮助处理 XX」补上具体能力 + 触发场景
正文罗列 5 个等价工具给一个默认，例外再开逃生口
写「2025 年 8 月前用旧接口」分「当前做法 / 旧模式（已弃用）」
同一概念换三种叫法全文统一术语
主文件塞进整本规范主文件摘要 + 旁路引用
只有步骤没有验收补「验证清单」和失败回退

路径一律用正斜杠：scripts/helper.py，不要写成 scripts\helper.py。

完整示例：代码评审 Skill ​

text
code-review/
├── SKILL.md
├── references/
│   └── standards.md
└── examples/
    └── sample-review.md

SKILL.md：

md
---
name: code-review
description: 按团队规范审查代码的质量、安全与可维护性。在评审合并请求、查看代码改动，或用户要求代码评审时使用。
---

# 代码评审

## 适用场景
- 合并前评审
- 用户明确要求 code review

## 不适用场景
- 大范围重构方案讨论（先出设计再评代码）
- 与本次改动无关的风格吹毛求疵

## 执行流程
1. 弄清改动目的与影响面
2. 按清单检查正确性、安全、可维护性、测试
3. 按反馈分级输出意见
4. 列出合并前必须项与可选建议

## 评审清单
- [ ] 逻辑正确，边界有处理
- [ ] 无明显安全问题（注入、越权、密钥泄露等）
- [ ] 符合项目约定
- [ ] 错误处理完整
- [ ] 测试覆盖本次改动

## 输出规范
- 必须修：合并前必须处理
- 建议改：值得改进
- 可选：不做也可

## 更多资料
- 详细规范：[references/standards.md](references/standards.md)
- 样例：[examples/sample-review.md](examples/sample-review.md)

写完自检 ​

  • [ ] description 含「做什么 + 何时用」和触发词
  • [ ] 有适用 / 不适用或等价边界
  • [ ] 步骤可执行，没有「适当 / 必要时」空话
  • [ ] 有输出规范或示例
  • [ ] 有完成标准（清单或校验命令）
  • [ ] 主文件够短；长内容已旁路且只链一层
  • [ ] 术语统一，默认方案唯一
  • [ ] 真用一次：相关请求下 Agent 会加载并按步骤执行

通过后再考虑分享到团队仓库或 Skill 市场。选型与 MCP 的配合见：Skill 与 MCP 异同。

面试怎么答：怎么写好一个 Skill ​

高频原题大致是：

你们 Agent 系统里的 Skill 是怎么写的？怎么保证一个 Skill 是高质量的？

表面问写法，实际在看 Agent 工程化：你会不会抽象任务、会不会把专家判断写进系统、有没有质量闭环。

面试官在听什么 ​

层次想听到什么
任务抽象什么适合 Skill 化，什么不适合
专家沉淀有没有决策树、反模式，而不只是「步骤说明」
质量保障有没有验证、评测、持续迭代

不要一上来只说「我会写 SKILL.md」。先亮这三层，再落到具体做法。

差答案 vs 好答案 ​

差（容易被追问住）：

就是给 AI 写指令，用 Markdown，告诉它什么时候触发、怎么做……

好（把 Skill 抬到能力单元）：

我不把 Skill 当成 Prompt 模板，而是 Agent 里可复用的任务能力单元。高质量 Skill 要有触发条件、专家决策逻辑、反模式约束、资源分层加载、验证闭环和迭代机制。目标不是偶尔答得好，而是在一类任务上稳定、可控、可复用。

一句话定调也很管用：

Skill 写得好不好，本质是信息架构题，不是「指令是否通顺」的文案题。

三层答题框架（建议按这个递进） ​

第一层：认知

  • Skill = 可复用任务能力，不是长 Prompt
  • 读者是 AI，不是人：少写背景、语气、版本记录；多写「现在该怎么判断」

第二层：设计

  • 值不值得做：反复出现 + 够复杂 + 熟手/新手差距大 + 要质量；翻译、一次性活别硬塞
  • 上下文成本：description 常驻（第三人称 + 何时用）→ SKILL.md 触发后再加载（宜短）→ scripts / references 按需
  • 专家判断：条件决策树 + 「不做什么」；「不做什么」比空泛的「保持专业」更能收窄行为
  • 自由度匹配：高风险（迁移、发布）先出计划再执行、低自由度；分析类（评审）给框架、留空间

第三层：工程

  • 脆弱、要一致的步骤 → 脚本化
  • 多步且顺序重要 → Checklist，防漏步
  • 关键步后强制验证，失败则停，不链式带错往下走
  • 写完用「写 Skill 的实例」和「用 Skill 的实例」对照测：漏步、误触发、决策分错了，再改回 Skill

可能的追问，怎么接 ​

追问接法要点
好不好的核心标准是什么？稳定可复用；触发准、判断像专家、输出可验收、可迭代
description 怎么写？第三人称；做什么 + 何时用；带触发词；忌「我可以帮你」
和普通文档有什么区别？文档给人读；Skill 是执行协议，要可检测的步骤与禁区
和 MCP 什么关系？Skill 管流程与判断；MCP 管外部能力连接；常组合，不互相替代（详见 Skill 与 MCP 异同）
举个你写过的例子？用本文「代码评审」或提交信息类：决策树 + 分级输出 + 清单/脚本

评分直觉（自己对照） ​

  • 基础分：写过 Skill / 知道有 SKILL.md
  • 高分：能讲清分层加载、description、决策树与反模式
  • 顶分：还能讲自由度光谱、Checklist、验证闭环、双实例迭代——说明真在项目里打磨过

把上文「先想清楚 → description → 正文决策树 → 脚本与自检」说圆，这道题基本就稳了。
