MCP 是什么：从协议到实践 ​

大模型本身只会「说」，不会真的查库、读文件、调内部 API。要让 Cursor、Claude Desktop 这类 Host 稳定地接上外部能力，就需要一套标准的连接方式。MCP（Model Context Protocol）就是干这件事的。

和 Skill、Rule 怎么分工，见：Skill、MCP、Rule 异同。

Anthropic 在 2024 年 11 月发布了这一开放协议，目标是标准化 LLM 应用与外部数据源、工具之间的通信。行业里常把它比作「AI 应用的 USB-C」：插头统一了，键盘、硬盘、网卡才能即插即用。

名字里的「模型上下文」容易误解。更准确地说，MCP 描述的是 MCP Host 与 MCP Server 之间的交互协议，模型只是 Host 里的推理引擎。

它解决了什么问题 ​

没有 MCP 之前，常见做法是：

  • 每个产品自己定义一套 Function Calling / Tool Schema
  • 同一个「查天气 / 读仓库」能力，要为 Cursor、Claude、自研 Agent 各写一遍适配
  • 工具能力绑死在某个客户端上，难以复用、难以分发

有了 MCP 之后：

  • 能力提供方只实现一次 MCP Server
  • 能力消费方（各类 Host）只要实现 MCP Client，就能发现并调用这些能力
  • 生态可以像插件市场一样生长，而不是每个 App 各搞一套私有协议

和模型侧的 Function Calling 并不对立：Function Calling 解决的是「模型如何表达要调哪个函数」；MCP 解决的是「Host 如何用统一协议连上一组可插拔的外部能力」。前者偏模型接口，后者偏工程集成。

发展与生态 ​

发布后很快被主流产品接住：

  • 微软：把 MCP 能力整合进 Azure OpenAI 等服务链路
  • GitHub：开源 github-mcp-server 等兼容实现
  • Cursor、Trae、VS Code（Cline、文心快码等）：逐步支持配置与调用 MCP Server

技术架构：Host / Client / Server ​

MCP 把「AI 应用 ↔ 外部系统」抽象成客户端–服务器模型，消息层基于 JSON-RPC 2.0。

三个核心角色：

  1. MCP Host：用户直接打交道的应用，例如 Claude Desktop、VS Code、Cursor、Trae
  2. MCP Client：跑在 Host 内部的通信代理，负责连 Server、解析协议、转发调用
  3. MCP Server：提供具体能力的轻量程序（读文件、调 API、查库等）

可以这么记：

  • Host = 壳（IDE / 桌面端）
  • Client = 插头上的协议芯片
  • Server = 真正干活的外设

一个 Host 通常可以同时挂多个 Server（浏览器、文件系统、数据库、GitHub……）。

MCP Server 提供什么能力 ​

MCP Server 常常是本机跑着的一个进程，名字里有 Server，但不一定是远程 Web 服务。常见用 Node.js、Python、Java 等实现。

协议侧通常暴露三类能力（不同 Server 可按需实现）：

能力作用典型例子
Tools可执行的动作（有副作用也常见）查天气、创建 Issue、跑一次查询
Resources可读的上下文资源文件内容、配置、文档片段
Prompts预置的提示 / 工作流模板「按某模板写 PR 描述」

日常用得最多的是 Tools：模型决定调哪个工具、带什么参数，Host 经 MCP 调到对应 Server，再把结果塞回对话上下文。

在编辑器里怎么用 ​

Cline、Trae、Cursor 等 Host 都支持配置 MCP。以 Cursor 为例，常见是在项目或用户配置里声明要启动的 Server，例如：

json
{
  "mcpServers": {
    "weather": {
      "command": "npx",
      "args": ["-y", "@example/weather-mcp-server"]
    }
  }
}

含义很直接：Host 用 command + args 拉起本地进程，再通过 stdio（或 SSE / HTTP 等传输）做 JSON-RPC 通信。具体字段名以当前 Host 文档为准，但「声明进程 + 协议发现工具」这一模式是共通的。

一次完整调用长什么样 ​

下面用「问纽约明天天气」这类场景串起来（对应多数 Host 的工具调用环）：

  1. Host 启动 MCP Server，完成 initialize 握手
  2. Client 调 tools/list，拿到 get_forecast、get_alerts 等工具描述
  3. 用户提问 → 模型决定调用 get_forecast，并给出参数
  4. Host 经 MCP 发起 tools/call
  5. Server 返回结果 → Host 再喂给模型 → 模型组织自然语言回答

通信底座：JSON-RPC 速览 ​

MCP 选用 JSON-RPC，是因为它轻量、无状态、不绑死传输层（stdio、HTTP、WebSocket 都可以驮一层）。

请求 ​

请求是一个 JSON 对象：

json
{
  "jsonrpc": "2.0",
  "method": "方法名",
  "params": {},
  "id": 1
}

关键字段：

  • jsonrpc：必填，固定为 "2.0"
  • method：必填，要调用的方法名，如 "tools/list"
  • params：可选，数组（位置参数）或对象（命名参数）
  • id：用于匹配请求与响应；若是不期待响应的 notification，可省略或为 null

成功响应 ​

json
{
  "jsonrpc": "2.0",
  "result": {},
  "id": 1
}

错误响应 ​

json
{
  "jsonrpc": "2.0",
  "error": {
    "code": -32601,
    "message": "Method not found",
    "data": null
  },
  "id": 1
}

读 MCP 抓包时，先分清：外层是 JSON-RPC 信封，内层 method / result 才是 MCP 语义（初始化、列工具、调工具等）。

MCP Server 从哪找 ​

想试用现成能力，可以从这些入口逛起（数量会变，以站点为准）：

  1. 官方 servers 仓库 — 官方示例与参考实现
  2. MCP.so
  3. mcpstore.co
  4. mcpmarket.com
  5. smithery.ai

选型建议：优先看是否开源、最近是否更新、权限范围是否过宽（尤其是能读全盘、能执行任意命令的 Server）。

小结 ​

  • MCP 是 Host 与外部能力之间的标准插头，不是模型本身的一部分
  • 架构上记住 Host / Client / Server，能力上优先理解 Tools
  • 报文层是 JSON-RPC；会读 initialize、tools/list、tools/call 就够排查大半问题

下一步可以：在 Cursor 里接一个官方示例 Server，随便问一句能触发工具的话，对着日志把三次 JSON-RPC 对上看一遍——比只读文档扎实得多。
