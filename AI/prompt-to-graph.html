从 Prompt 到 Graph：Agent 的五层能力演进 ​

做 AI 应用时，很多人一上来就堆 Prompt，或直接冲向「多智能体」。更稳妥的看法是：能力是一层层叠上去的——

Prompt → Context → Harness → Loop → Graph

它们不是互相替代的产品名，而是同一条能力演进线上的五个台阶：先让模型「听得懂」，再让它「看得到」，再「可控地动手」，再「多步推进」，最后才是「多节点编排」。

编码 Agent（Cursor、Claude Code 等）也走同一条线；下文例子以客服、研报、业务自动化为主，编码只作辅证。和「Agent 是什么」的关系见：Agent 概念。

text
Prompt   指令与角色
   ↓
Context  知识与状态
   ↓
Harness  工具、权限、校验
   ↓
Loop     思考 → 行动 → 观察
   ↓
Graph    多节点分支 / 并行 / 审批

Prompt：先把话说清楚 ​

Prompt 是对模型的直接指令：角色、目标、输出格式、禁止事项。

例子：

  • 客服：「你是售后助手，只根据知识库回答；不确定就转人工。」
  • 研报：「根据下方材料写 800 字摘要，分：结论 / 证据 / 风险。」

这一层解决的是：意图对齐。写得好，单轮质量会明显上去。

局限也很清楚：

  • 没有业务事实（库存、订单、最新公告）时只能猜
  • 不能查库、发邮件、改工单
  • 多轮里容易「忘了刚才约定」——除非你把约定反复塞进下一轮

实践要点：角色、边界、输出模板写死；把「不要做什么」写清楚，比堆形容词更有用。

Context：把该看的东西放进视野 ​

当「只会说话」不够时，需要 Context：在调用模型前，把相关信息注入上下文。

常见来源：

类型例子
检索（RAG）客服知识库、产品 FAQ、政策条文
会话状态当前工单号、用户已选套餐、上一轮结论
业务快照CRM 档案、订单状态、库存数字
结构化附件表格、JSON、合同摘要

客服场景：用户问「我的退款到哪了？」——仅靠 Prompt 不够，要把订单状态、退款规则、历史沟通摘要放进 Context，回答才站得住。

研报场景：把招股书章节、财报关键指标、近期公告检索结果塞进上下文，再要求按模板输出。

注意：Context 不是越多越好。噪声多了，模型会抓错重点。实践上更关心：

  • 检索是否命中、是否过期
  • 是否做了去重与截断
  • 关键权限数据是否该进模型视野

一句话：Prompt 管怎么说，Context 管看见什么。

Harness：让「能说」变成「可控地做事」 ​

有了指令和资料，下一步往往是接工具：查工单、调 CRM、发通知、写文档。真正难的不是「接上 API」，而是 Harness（运行时护栏）——约束 Agent 可以动什么、怎么动、动坏了怎么办。

Harness 通常包括：

  • 工具边界：能查哪些接口、能不能写、写前是否二次确认
  • 权限与审计：谁以什么身份调用；关键操作留痕
  • 格式与契约：工具入参校验、返回结构校验，失败要可读
  • 配额与超时：单次调用上限、重试次数、总耗时预算
  • 安全策略：脱敏、禁止外泄字段、危险动作黑名单

客服自动化例子：允许「查询订单 / 发起退款申请」，但「直接打款」必须人工点确认——这就是 Harness，而不是再写一句「请谨慎」的 Prompt。

和现有概念的对应（编码场景更明显，通用场景同理）：

概念更偏哪一层
Skill流程与规范（常挂在 Loop / Harness 上）
MCP外部工具与数据通道（Harness 的「手脚」）
Agent 运行时把 Prompt/Context/工具/循环装在一起的壳

细节对比见：Skill 与 MCP 异同。

Loop：多步推进直到结束 ​

单次「读 Context → 调一次工具 → 出答案」往往不够。复杂任务需要 Loop：在结束条件满足前，反复 思考 → 行动 → 观察。

text
目标进入
   ↓
[思考] 下一步做什么？
   ↓
[行动] 调工具 / 写中间结果 / 问人
   ↓
[观察] 结果或报错
   ↓
完成？──否──→ 回到思考
   │
  是
   ↓
交付结论

这就是常见的 ReAct 形态，也是 Agent 的核心循环。

自动化例子：夜间对账——拉账单 → 比对差异 → 分类异常 → 生成报告 → 超阈值则建工单。每一步依赖上一步观察结果，靠 Loop 串起来。

实践检查点：

  • 结束条件写清：成功标准是什么，何时放弃
  • 步数 / 超时上限：防止空转烧钱
  • 失败回退：换策略、降级、转人工，而不是无限重试
  • 中间状态可观测：方便排障与审计

Loop 解决的是「一件事要走很多步」；还没解决「很多种路径、多个角色怎么协作」。

Graph：从单环到多节点编排 ​

当流程出现分支、并行、多人（或多 Agent）分工时，单 Loop 会变臃肿。这时升到 Graph：把任务拆成节点，用边表达依赖与路由。

研报流水线示意：

text
          ┌─→ [检索公告] ─┐
[选题] ───┼─→ [拉财报]   ─┼─→ [分析撰写] → [合规审校] → [人工签发]
          └─→ [竞品对比] ─┘

典型能力：

  • 分支：投诉类型不同，走退款 / 换货 / 技术排查不同子图
  • 并行：检索、拉数、竞品可同时跑，再汇总
  • 人工节点：高风险步骤插入审批闸门
  • 多角色：研究员 Agent、风控 Agent、编辑 Agent 各守一段

客服升级例子：L1 机器人 Loop 解不了 → 路由到「退款子图」或「技术排障子图」→ 仍失败则进人工队列。这是 Graph 路由，而不是把所有 if/else 塞进一个超长 Prompt。

注意：Graph 成本更高（编排、状态机、可观测性、测试）。多数业务先把 Prompt + Context + Harness + 单 Loop 做稳，再按真实分支复杂度上图。

总对照表 ​

层解决什么缺它时的症状实践检查点
Prompt意图、角色、输出格式答非所问、格式乱、越界胡说边界与模板是否写死
Context看见事实与状态瞎编业务细节、答非最新政策检索质量、截断、权限
Harness可控地调用工具乱调 API、无审计、一次写挂生产权限、校验、超时、确认
Loop多步完成单一目标一步做不完、不会根据结果调整结束条件、步数上限、回退
Graph分支 / 并行 / 多角色协作单环里塞满 if、难以维护与扩容节点边界、人工闸门、可观测

选型口诀：能用下一层解决的问题，不要急着跳两层。 客服 FAQ 可能到 Context 就够；对账自动化要 Loop；跨部门研报签发才值得 Graph。

小结 ​

  • 五层是能力叠层，不是五个互斥产品
  • Prompt 对齐说法，Context 对齐事实，Harness 对齐安全与工具，Loop 对齐多步执行，Graph 对齐复杂编排
  • 落地时先问：卡在「不会说」「看不见」「不敢动」「走不完」「路径太乱」的哪一层
  • Agent / Skill / MCP 是工程上的组装方式；可以分别挂在 Harness 与 Loop 上，详见 Agent、Skill、MCP

下一步建议：挑一个真实业务流，标出当前停在第几层，再只升一层做验证——比一上来画多智能体图更省时间。
