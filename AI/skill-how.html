Skill 生效原理 ​

Skill 不是插件，也没有独立进程。磁盘上多一个 SKILL.md，并不会自动跑脚本、也不会每条消息都塞进模型。

真正生效靠三件事串起来：

  1. 被扫描到：Host（Cursor、Claude Code 等）启动时扫描约定目录
  2. 被选中：模型根据 description（或你手动 /技能名）判断「现在该用这个」
  3. 被读进上下文：Agent 用读文件 / 跑命令的方式把正文加载进来，再当执行协议去跟

概念与怎么写见：Skill 说明、如何编写 Skill。文件是怎么落到这些目录的，见：npx skills 怎么安装。

三级渐进披露 ​

这套加载策略叫 渐进披露（Progressive Disclosure）：上下文里先只放目录，真正相关时才翻开章节，需要附录时再翻附录。这样可以装很多 Skill，而不把窗口一次性撑爆。

级别何时进入上下文装什么
L1 元数据会话启动，几乎始终在只把 name + description 放进系统提示（每个大约一百来个 token）
L2 指令正文意图对上，或你打了 /技能名才去读完整 SKILL.md
L3 附属资源正文里点名需要时再打开 references/，或去跑 scripts/（脚本只带回运行输出）

flowchart TD
  A[会话启动] --> B[扫描 Skills 目录]
  B --> C["L1：只注入 name + description<br/>约 100 token / 个"]
  C --> D[用户发消息]
  D --> E{description 匹配<br/>或用户打了 /技能名?}
  E -->|否| F[当普通任务处理]
  E -->|是| G[L2：读取完整 SKILL.md 正文]
  G --> H[按步骤执行]
  H --> I{还要参考资料或脚本?}
  I -->|读文件| J[L3：按需打开 references]
  I -->|跑命令| K[L3：执行 scripts，只把输出带回]
  I -->|否| L[按约定产出结果]
  J --> L
  K --> L

由此直接推出三条写作约束：

  • description 决定会不会被用上。 L1 里模型只看得见这一句。写糊了，等于这个 Skill 对 Agent 不存在。写法见：如何编写 Skill
  • 正文太长会拖累每一次触发。 长规范、大表、完整 API 放到 references/，主文件只链一层
  • 脚本是「手脚」，不是「自动挂载」。 Agent 按正文去终端执行，带回的是运行输出，不是把整份脚本贴进 prompt

官方说明可对照：Agent Skills 规范、Anthropic：Equipping agents with Agent Skills、Cursor Skills。

从哪被扫描到 ​

Host 会递归查找「目录 + SKILL.md」。常见位置：

范围典型目录
项目内（跟仓库走）.cursor/skills/、.agents/skills/、.claude/skills/
本机全局~/.cursor/skills/、~/.agents/skills/、~/.claude/skills/

兼容层因产品而异：Cursor 还会扫 .codex/skills/；Claude Code 以 .claude/skills/ 为主。身份来自包含 SKILL.md 的那一层文件夹名，外层分类目录只是整理用。

Monorepo 里也可以把 Skill 放在子包旁（如 apps/web/.cursor/skills/），部分 Host 会把它自动限定在该子树相关的文件上。从 GitHub 一键写入这些目录，见：npx skills 怎么安装。

两种触发方式 ​

方式谁决定用典型动作
自动匹配Agent 拿用户意图去对 description你说「帮我做代码评审」，它自己去读评审 Skill
显式调用你点名输入 /技能名，或用 @ 把 Skill 贴进当前消息

可调开关（字段名以 Cursor / Agent Skills 实践为准，其他 Host 可能略有差异）：

  • disable-model-invocation: true：关掉自动匹配，只在你打 /技能名 时进入上下文（行为接近以前的 Slash Command）
  • paths：按 glob 限制「正在处理哪些文件时才露出这个 Skill」，避免无关任务也被匹配上

显式调用通常只作用于当前这一条消息。若要整段会话都带着同一套协议，需要 Host 提供的「自定义模式 / Custom Mode」一类能力，而不是指望 Skill 自己常驻。

和 Rules 差在哪（所以「写了不等于生效」） ​

完整对照见：Skill、MCP、Rule 异同，Rule 写法见：Rule。

Rules（规则）Skill
进上下文的方式常驻或按 glob 自动注入全文先只放目录（L1），匹配后再读正文（L2）
适合什么短约束、始终要遵守的规范按场景启用的流程、清单、脚本
写长了会怎样每条消息都占窗口未触发时几乎不占窗口

所以：把 200 行排障手册塞进 alwaysApply 的 Rule，和做成 Skill，成本完全不同。Skill 能装得多、写得细，前提是 L1 的 description 足够让模型「想起来去打开它」。

用户的明确指令（对话里的要求、AGENTS.md / CLAUDE.md 等）优先级通常高于 Skill。Skill 和用户指令打架时，以用户为准——这也是「没生效」的一种常见原因。完整对照见：Skill、MCP、Rule 异同；Rule 怎么写见：Rule。

写了却没生效，先查这几项 ​

  1. 目录不对或没有 SKILL.md：没被扫描到，L1 都进不去
  2. description 没有触发词：用户说的是「超时 / 白屏」，描述里却只写了「帮助处理问题」
  3. 开了 disable-model-invocation：必须手动 /技能名，等自动匹配会一直等不到
  4. paths 太窄：当前打开的文件对不上 glob，Skill 根本不会出现在候选里
  5. 正文与更高优先级指令冲突：用户说「先别跑测试」，Skill 里写「必须先跑测试」→ 以用户为准
  6. 以为脚本会自动执行：没有。Agent 只有在读到正文、并且决定执行那一步时，才会去跑 scripts/
