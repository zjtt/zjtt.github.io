Skill、MCP、Rule 的异同 ​

四样东西经常堆在一个 Agent 产品里：Rule、AGENTS.md、Skill、MCP。前三样都是「给模型看的字」，MCP 是「给 Host 插的工具」。不要用「能不能跑命令 / 能不能看 git」来分 Skill 和 MCP，Skill 里的脚本照样能 git diff。

分篇说明：Skill、Rule、AGENTS.md、MCP。Skill 怎么进上下文：生效原理。

相同点 ​

  • 都是为了让 Agent 少临时发挥：有约定、有手脚、有禁区
  • 都可以进 git，变成团队资产
  • 都可以和 Cursor、Claude Code 等 Host 一起用
  • Rule / AGENTS.md / Skill 都没有独立进程，只是磁盘上的说明；MCP 有进程（或远程服务）

不同点（一句话） ​

人话典型形态
AGENTS.md这个仓库怎么干活根目录一份 Markdown
Rule这些话尽量每次都遵守（或改某类文件时遵守）.cursor/rules/*.mdc
Skill做这一类任务时按这套步骤SKILL.md + 可选脚本
MCP去连某个外部系统Server + 工具 schema

加载成本也不一样：

怎么进上下文写长了会怎样
Rule / AGENTS.md常驻或按路径，全文进去每条消息都占窗口
Skill先注入 name + description，对上了才读正文没触发时几乎不占
MCP工具列表给模型看；真正执行发生在 Server工具太多会干扰选型，但不会把说明书全文塞进每一轮

用同一句话看该写哪 ​

用户说：「这个接口超时了，帮我查，按我们组的格式给结论。」

  • AGENTS.md：pnpm test、日志脚本在 script/、不要用 rm（仓库公约，跟这次超不超时无关也会用到）
  • Rule：改监控配置时禁止提交密钥（短禁令，always 或 glob）
  • Skill：收集时间/环境 → 查日志 → 定级 → 结论必须有影响面和止血（流程）
  • MCP：Sentry search_errors（线上数据不在 git 里）

只有 Skill：步骤清楚，但可能查不到线上错误。只有 MCP：能拉 JSON，结论像倒垃圾。只有 Rule：每条消息都带着「别提交密钥」，但没人告诉它排障怎么走。

代码侧再拆一次：

你要的写哪
「本仓库用 pnpm，不要动 dist/」AGENTS.md
「*.scss 禁止 flex gap」Rule（glob）
「review 意见必须分成必须修 / 建议改」Skill
「看当前分支 git diff」Skill 脚本或直接让 Agent 跑 git，不必 MCP
「把意见发到 GitHub PR 上 / 查 org 的 Issue」MCP（或 gh）。这不是本地 git 对象

Skill 和 MCP 容易糊的地方 ​

两边都能「做事」。本地 git log 放 Skill 的 scripts/ 就够。GitHub MCP 也能列 commit。所以「看 git」不是分界。

改问：这是当前工作区的一条命令，还是要插在 Host 上、换仓库也能用的服务？

  • 当前 clone 里有的 → Skill 脚本 / 终端
  • 要登录态、跨项目、结构化入参（Sentry、GitHub 网站、内部 RPC）→ MCP
  • Skill 脚本 ≠ MCP：脚本跟这份 SKILL.md 走；MCP 跟某一个 Skill 解耦

和 Rule 容易糊的地方 ​

Rule 和 Skill 都是 Markdown 说明，差别是加载策略：

  • 短、每次都不能忘 → Rule（或 AGENTS.md）
  • 长、按场景才用 → Skill

把 200 行排障手册写成 alwaysApply 的 Rule，等于每聊一句都带一本手册。

AGENTS.md 和 Rule 都偏常驻。差别是可移植 vs 细粒度：仓库怎么跑写 AGENTS.md（别的 Agent 也能读）；只在 Cursor 里按文件类型收紧写 Rule。同一条禁令写一份就行。

怎么选 ​

  1. 这个仓库的命令、目录、总禁令 → AGENTS.md
  2. 改某类文件时的短约束、Cursor 专属习惯 → Rule
  3. 一类任务的步骤、清单、输出模板 → Skill
  4. 当前仓库 git / 脚本做不完、要接外部系统 → MCP
  5. 流程要稳又要打远程 → Skill + MCP：Skill 写第几步调哪个工具

优先级大致是：你当轮说的话 > AGENTS.md / CLAUDE.md > Rule > Skill。Skill 和用户指令打架时，听用户的。
