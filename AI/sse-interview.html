SSE 面试题 ​

面向 AI 流式输出场景的高频题。配套实现见：前端流式输出。

1. SSE 是什么？怎么用？ ​

什么是 Server-Sent Events？前端怎么接？

简答：

  • SSE 是基于 HTTP 的单向服务器推送：服务端持续往客户端写事件流，客户端只读。
  • 响应头一般是 Content-Type: text/event-stream，且常配合 Cache-Control: no-cache、保持连接不关。
  • 浏览器原生用 EventSource(url)；AI 对话里更常用 fetch + ReadableStream（见第 5 题）。

Content-Type 是什么（白话）：

HTTP 里贴在数据上的标签，告诉对方：「这坨东西是什么格式、该怎么拆」。

像快递箱贴纸——写「生鲜」就按生鲜收。SSE 响应贴的是：

http
Content-Type: text/event-stream

意思是：body 不是一整包 JSON，而是持续的事件流文本（data:、空行那套），要一边收一边解析。

Content-Type对方怎么理解
application/json整段是一个 JSON
text/html是网页
text/event-stream是 SSE 流

注意：Accept 是客户端说「我希望你按什么格式回」；Content-Type 是实际发出去的那份数据贴的标签。两者经常成对出现，但不是一回事。

js
const es = new EventSource('/api/stream')
es.onmessage = (e) => console.log(e.data) // 默认 event: message
es.onerror = () => { /* 断线后浏览器会自动重连 */ }
// es.close() 主动断开

2. SSE vs WebSocket vs 长轮询？ ​

三者区别？什么时候用 SSE？

SSEWebSocket长轮询
方向服务端 → 客户端全双工伪实时（反复请求）
协议普通 HTTP独立 ws 协议普通 HTTP
断线浏览器可自动重连需自己做心跳/重连靠下次请求
典型场景LLM 打字机、通知、进度聊天、协同、游戏兼容差环境的兜底

**一句话：**只要「服务端持续推、客户端几乎不发」——尤其是 AI token 流——优先 SSE；要双向高频互动再用 WebSocket。

3. SSE 消息格式长什么样？ ​

data / event / id / retry 分别干什么？

事件之间用空行分隔；一行一个字段：

text
id: 42
event: token
retry: 3000
data: {"text":"你"}
data: {"text":"好"}
字段作用
data载荷；多行 data 会用 \n 拼成一条消息
event事件名；前端 addEventListener('token', ...)；缺省为 message
id事件 id；重连时浏览器带上 Last-Event-ID
retry重连间隔（毫秒），改客户端默认重试时间

注释行以 : 开头，可当心跳，客户端忽略。

4. 断线重连和 Last-Event-ID 怎么讲？ ​

网络抖一下会怎样？服务端怎么续传？

简答：

  1. EventSource 在连接异常时会自动重连（可用 retry 调间隔）。
  2. 若上次推过带 id: 的事件，重连请求会带请求头 Last-Event-ID。
  3. 服务端按这个 id 从断点继续推，避免整段重放；没做 id 就只能从头或丢中间段。

面试加分：别以为「断点续传」就等于「每条消息只会出现一次」。

打个比方：快递员说「从你签收的上一单接着送」。但有时你其实已经收到第 42 单了，签收回执还没走完网络就断了——对方以为你没收到，重连后又把第 42 单送了一遍。你手里就会出现两份一样的东西。

所以 SSE 更常保证的是：尽量别漏（至少送到一次），而不是 绝对只送一次。

业务上怎么防傻：给每条消息一个自己的业务编号，处理过就跳过；或者做成「再执行一遍也没关系」（幂等）。

5. 为什么 AI 场景常用 fetch 流，而不是只用 EventSource？ ​

EventSource 不够用在哪？

EventSource 限制多（规格如此，不是「难写」而是根本没这项能力）：

  • 请求方法固定为 GET，不能 POST / PUT
  • 不能自定义请求 Header（没有设置 headers 的 API）；鉴权 Token、租户头等带不了
  • 不能带请求 Body（对话历史、模型参数没法塞进 body）
  • 唯一沾边的是 { withCredentials: true }：可以带上 Cookie，但这不是自定义 Header，也解决不了 POST body

所以 AI 对话场景几乎都会换成 fetch + ReadableStream，或封装库 @microsoft/fetch-event-source。

所以业务里常见：

js
const res = await fetch('/api/chat', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${token}`,
    Accept: 'text/event-stream',
  },
  body: JSON.stringify({ messages }),
  signal: controller.signal, // 可取消
})
const reader = res.body.getReader()
// 按 chunk 解码，再按 SSE 规则切事件、拼 data

上面两个头别混：

  • 请求里的 Content-Type: application/json：说的是我发出去的 body（messages）是 JSON
  • 请求里的 Accept: text/event-stream：说的是我希望你回 SSE 流
  • 真正流起来时，响应头里还应是 Content-Type: text/event-stream（服务端贴的标签）

口述要点：换的是「怎么连」，不是「协议长什么样」。

  • 服务端吐出来的还是 SSE 文本（data:、空行那些），规矩没变。
  • 变的是客户端：不用 EventSource 自动帮你读，改用 fetch 自己发请求、自己读流。
  • 图的就是三样 EventSource 做不到的事：
    • POST：把整段对话、模型参数放进 body
    • Header：带上 Authorization 等鉴权
    • AbortController：用户点「停止生成」立刻掐断请求

ReadableStream 是什么（白话）：

可以把 res.body 想成一根水管：服务端一边往里灌水（token 一块一块来），前端一边用杯子舀，不用等整桶装满。

  • res.body 就是这根水管（ReadableStream）
  • getReader() 是拿一个读杯（reader）
  • 循环 reader.read()：每次得到一小块二进制 value（chunk）；done === true 表示水放完了
  • 再用 TextDecoder 把二进制转成字符串，按 SSE 规则切开 data:，拼到页面上

和 EventSource 的差别：EventSource 帮你「接好水管 + 自动拆成事件」；fetch 只给你水管，拆包、拼字、取消都要自己写，但换来 POST / Header / 取消的自由。

6. @microsoft/fetch-event-source 原理是什么？ ​

它和手写 fetch + ReadableStream、原生 EventSource 是什么关系？

**一句话：**协议还是 SSE；底下仍是 fetch + ReadableStream；库把「拆包、重连、Last-Event-ID」帮你做了，API 长得像 EventSource。

不是浏览器原生 EventSource，也不是另一套协议。

流水线（库在干什么） ​

text
fetch(url, { method, headers, body, signal })
    → response.body（ReadableStream 水管）
    → getBytes：循环 reader.read() 舀字节
    → getLines：按换行切行（半包先攒着）
    → getMessages：认 data / event / id / retry，空行凑成一条事件
    → 调用你的 onmessage({ data, event, id, ... })

业务侧通常只写：

js
import { fetchEventSource } from '@microsoft/fetch-event-source'

await fetchEventSource('/api/chat', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Accept: 'text/event-stream',
  },
  body: JSON.stringify({ messages }),
  signal: ctrl.signal,
  onmessage(ev) {
    // ev.data 已是拆好的字符串，常再 JSON.parse
  },
  onerror(err) {
    throw err // 不抛会按默认间隔自动重连
  },
})

比手写多出来的几件事 ​

能力白话
POST / 自定义 Header参数直接传给 fetch，所以能带 JSON body、鉴权头
Abort内部还有自己的 AbortController，和你传入的 signal 联动
Last-Event-ID解析到 id: 就记着，自动重连时带上
默认自动重连onerror 若不抛错，会 setTimeout 后再连一次
页签隐藏默认切走会断、回来再连；可设 openWhenHidden: true 切后台也不主动断

三种写法怎么记 ​

方案本质你自己要写什么
原生 EventSource浏览器内置几乎不用拆包，但只能 GET，不能自定义 Header/Body
手写 fetch + Stream自己接水管read、拼 buffer、按 SSE 切行切事件都要自己写
@microsoft/fetch-event-source还是 fetch 流库帮你拆成 onmessage；重连要在 onerror 里 throw 才能停

面试口述：「我们用的库本质是 fetch 流式读 SSE，不是 EventSource；图的就是 POST 和自定义头。」

7. 为什么本地顺、过了 Nginx / CDN 就不流了？ ​

流式被缓冲怎么排查？

常见原因是中间层把响应攒完再吐：

  • 响应头声明：Content-Type: text/event-stream、Cache-Control: no-cache
  • Nginx：X-Accel-Buffering: no，关掉 proxy buffering
  • 避免 gzip 把小 chunk 捏成大块（或关闭对该接口的压缩）
  • 心跳：定期发注释行 : ping 或空事件，防止空闲超时断连
  • HTTP/1.1 下注意代理超时、连接数；能上 HTTP/2 对多路复用更友好

8. AI 流式（token）怎么接到 SSE 上？ ​

从模型 chunk 到页面打字机，链路怎么说？

text
模型流式 API（chunk）
    → 后端转成 SSE：data: {"delta":"..."}\n\n
    → 前端按事件解析，增量 append 到 UI
    → 结束帧（如 event: done / data: [DONE]）收尾
    → 出错用 event: error 或非 2xx，前端停写并提示

答题结构：

  1. 为什么 SSE：单向推 token，实现简单，走现有 HTTP/鉴权
  2. 帧约定：delta / done / error 三类事件谈清
  3. 前端：缓冲未拼完的半包；AbortController 停止生成
  4. 体验：先渲染再精细排版；失败可重试且尽量带 Last-Event-ID 或业务 cursor

9. 上线必问：代理缓冲、心跳、取消、错误帧（含断网半截消息） ​

面试常追问：上了生产还会踩什么？进电梯断了怎么办？

代理缓冲 ​

中间层（Nginx / CDN / 网关）可能把响应攒完再一次性吐，本地直连看着是流，过了代理就「等很久然后整段出来」。

  • 响应：Content-Type: text/event-stream、Cache-Control: no-cache
  • Nginx：X-Accel-Buffering: no
  • 小心 gzip / 过长超时把小 chunk 捏死或掐线

（细节见第 7 题。）

心跳 ​

连接空闲太久，代理或浏览器可能当死连接掐掉。服务端定期发无关紧要的注释行即可，例如：

text
: ping

客户端忽略；目的是让链路上一直有字节在动。

取消 ​

用户点「停止生成」要用 AbortController.abort()（或库的 signal）立刻掐 fetch，别只藏 UI、后台还在收流烧配额。

错误帧 vs 传输错误 ​

两件事别混：

类型例子前端怎么做
业务错误帧event: error / data 里带错误码，连接可能还在停写、提示文案，按约定关流
传输层错误进电梯断网、Failed to fetch、读流抛错 → 库的 onerror关连接；要不要自动重连是产品策略

@microsoft/fetch-event-source 默认会重连；很多业务（含对话类）在 onerror 里 throw 关掉自动重试，避免弱网疯狂重打。

进电梯：会不会消息显示一半？ ​

会。 流一断，已经画到屏幕上的还在，后面的事件不会再来。

常见长相：

  1. 流程做到一半：前面的文案 / 卡片上屏了，后面的结束帧没到
  2. 打字机播到一半：整段其实已到前端，动画没播完就断了

常见处理（选一种说清即可）：

  • Toast「网络异常」，解锁输入，不自动重连
  • 恢复后拉历史 / 任务结果对齐，而不是盲目重放整段 SSE
  • 有 id / 业务 cursor 时可做断点续传，但要防重复插入（至少一次投递，见第 4 题）

速记 ​

  • SSE = HTTP 上的服务端单向事件流
  • 格式记住：data + 空行；id 服务于断点续传
  • AI 项目：手写 fetch 流，或 @microsoft/fetch-event-source（本质仍是 fetch + 拆 SSE）
  • 上线必问：代理缓冲、心跳、取消、错误帧；断网会半截展示，重连策略要主动设计（详见第 9 题）
