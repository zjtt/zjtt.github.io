HTTP：从 0.9 到 3 ​

HTTP 是浏览器和服务器之间的通信语言。协议一直跟着浏览器的需求走：先能传 HTML，再能传多种文件，再把连接和传输效率补上来。

这篇按演进顺序看每个版本补了什么、又留下了什么瓶颈。

HTTP/0.9：只传 HTML ​

1991 年的 HTTP/0.9 需求很单纯：在网上传一份很小的 HTML。流程也极简：

mermaid
sequenceDiagram
    participant C as 客户端
    participant S as 服务器

    C->>S: TCP 三次握手
    C->>S: GET /index.html
    S->>C: ASCII 字符流（HTML）
    Note over C,S: 传完即断开 TCP

三个特点：

  1. 只有请求行，没有请求头、请求体。GET /index.html 已经够用。
  2. 没有响应头。服务器直接把文件内容吐回去。
  3. 只传 ASCII 文本 HTML，传完就关连接。

当时页面小、资源少，短连接完全够用。

HTTP/1.0：用请求头 / 响应头谈清楚 ​

1994 年后浏览器开始流行，页面里不再只有 HTML，还有 JS、CSS、图片、音视频，编码也不止 ASCII。0.9 那种「只丢一行 GET」的对话方式撑不住了。

HTTP/1.0 的核心补丁是 请求头 + 响应头（Key-Value）。浏览器先说清楚自己要什么，服务器再声明实际给了什么。

mermaid
sequenceDiagram
    participant C as 浏览器
    participant S as 服务器

    C->>S: TCP 三次握手
    C->>S: 请求行 + 请求头
    S->>C: 响应行 + 响应头
    S->>C: 响应体
    Note over C,S: 传完即断开 TCP

内容协商：多类型文件怎么传 ​

要支持多种文件，至少要谈清四件事：类型、压缩、语言、编码。

请求头（浏览器期望）：

http
accept: text/html
accept-encoding: gzip, deflate, br
accept-charset: ISO-8859-1, utf-8
accept-language: zh-CN, zh

响应头（服务器实际结果）：

http
content-encoding: br
content-type: text/html; charset=UTF-8

注意：协商结果以响应头为准。浏览器要 gzip，服务器可能只支持 br，最终按 content-encoding: br 解压。

1.0 顺手补上的能力 ​

能力作用
状态码用响应行告诉浏览器这次处理得怎么样（200、404、500…）
Cache缓存已下载资源，减轻服务器压力
User-Agent让服务器统计客户端环境

1.0 仍然是 短连接：一次 HTTP 通信 = 建 TCP → 传数据 → 断 TCP。页面引用少、文件小时问题不大。

HTTP/1.1：把连接和动态内容补上 ​

页面越来越重，一个页面可能引用几百个资源。每次请求都三次握手、再挥手，开销太大。1.1 主要在这个方向打补丁。

1. 持久连接（Keep-Alive） ​

一个 TCP 连接上可以连续发多个 HTTP 请求，直到浏览器或服务器明确断开。

mermaid
sequenceDiagram
    participant C as 浏览器
    participant S as 服务器

    C->>S: TCP 三次握手
    C->>S: HTTP 请求 1
    S->>C: HTTP 响应 1
    C->>S: HTTP 请求 2
    S->>C: HTTP 响应 2
    C->>S: HTTP 请求 3
    S->>C: HTTP 响应 3
    Note over C,S: 空闲超时或 Connection: close 后才断开
  • HTTP/1.1 默认开启持久连接，不必额外声明。
  • 不想复用时，请求头加 Connection: close。
  • HTTP/1.0 其实也能 Keep-Alive，但要显式声明；1.1 才变成默认。
  • 浏览器对 同一域名默认最多 6 条 TCP 持久连接。

好处：少握手、少挥手，服务器负担更小，整体耗时更短。

2. 管线化：想解决队头阻塞，但没做成 ​

持久连接里，请求仍是「等前一个响应回来，再发下一个」。某个请求卡住，后面全堵，这就是 HTTP 队头阻塞。

1.1 试过 管线化（pipelining）：把多个请求整批发出去。但服务器仍必须 按请求顺序 回响应。Firefox、Chrome 都试过，后来都关掉了。真正解决要等到 HTTP/2 的多路复用。

mermaid
sequenceDiagram
    participant C as 浏览器
    participant S as 服务器

    Note over C,S: 持久连接：必须等响应
    C->>S: 请求 1
    S->>C: 响应 1
    C->>S: 请求 2
    Note right of S: 若这里卡住
    C--xS: 请求 3 发不出去

    Note over C,S: 管线化：请求可整批发，响应仍按序
    C->>S: 请求 1、2、3
    S->>C: 必须先回 1，再回 2、3

3. Host：一台机器挂多个域名 ​

1.0 默认「一个 IP 绑一个域名」。虚拟主机出现后，多个域名可以共用一个 IP。1.1 请求头加了 Host，服务器按域名分流。

4. Chunked Transfer：动态内容也能传完 ​

1.0 要求响应头带完整 Content-Length，浏览器按这个长度收数据。服务端动态生成页面时，发之前往往不知道最终大小。

1.1 用 分块传输（chunked）：数据切成若干块，每块前面带上 本块长度，最后发一个长度为 0 的块表示结束。

5. Cookie 与安全 ​

1.1 还引入了客户端 Cookie（后续请求自动带上），以及更完整的认证等安全机制。HTTPS / TLS 是独立一层，不是 HTTP/1.1 本身发明的。

缓存方面，1.1 补了 Cache-Control、ETag 等字段，细节见 浏览器缓存。

HTTP/2：一条连接上并行传 ​

1.1 已经有持久连接、同域名最多 6 条 TCP，再配 域名分片，下载会快很多：100 个资源大约从 100 * n * RTT 降到 100 * n * RTT / (6 * 分片域名数)。

域名分片（domain sharding）是 HTTP/1.1 的并行下载技巧。浏览器按 主机名 限连接，www.example.com 最多 6 条；把图片、脚本拆到 img1.cdn.com、img2.cdn.com、static.example.com 上，浏览器就把它们当成不同域名，每个都能再开 6 条。3 个分片就是最多 18 条并行连接。CDN 很适合干这个：多个子域名指到同一套边缘节点，既绕开 6 连接上限，又就近下载。

HTTP/2 一个域名一条连接就能多路复用，再分片反而会多几次握手、多几次慢启动，所以 HTTP/2 之后一般不再做域名分片。

即便如此，带宽还是经常用不满。100M 带宽理论下行约 12.5MB/s，加载页面时可能只用到 2.5MB/s。主要有三个原因。

带宽为什么用不满 ​

  1. TCP 慢启动。连接刚建好时发得很慢，再逐渐加速。HTML / CSS / JS 这些关键文件往往不大，却正好赶在慢启动阶段请求，首次渲染会被拖后。慢启动是 TCP 防拥塞的策略，应用层改不了。
  2. 多条 TCP 抢同一条带宽。一个页面 200 个文件、3 个 CDN，就是 6 * 3 = 18 条连接。带宽不够时大家一起减速，连接之间又没法协商「CSS/JS 优先、图片靠后」。
  3. HTTP 队头阻塞。同一条 TCP 上同时只能处理一个请求，前面的卡住，后面的只能等。带宽和 CPU 都在空转，浏览器也没法提前解码后面的资源。

慢启动和抢带宽来自 TCP 本身；队头阻塞来自 HTTP/1.1。当时还换不掉 TCP，HTTP/2 的办法是：一个域名只保留一条 TCP 长连接（慢启动只走一次，也不再多连接互抢），再用多路复用把 HTTP 层的队头阻塞拆掉。

多路复用 ​

每个请求有自己的 stream ID。浏览器随时可以把请求发出去，不必等上一个结束；服务器也可以按自己的节奏返回，甚至先回头、再回体。浏览器按 ID 把同一条流的数据拼回完整响应。

mermaid
sequenceDiagram
    participant C as 浏览器
    participant S as 服务器

    C->>S: stream1 index.html
    C->>S: stream2 foo.css
    C->>S: stream3 bar.js
    S->>C: stream1 响应头
    S->>C: stream3 响应头
    S->>C: stream1 响应体
    S->>C: stream2 响应头 + 体
    Note over C: 按 stream ID 拼回完整响应

因为数据是一帧一帧传的，高优先级请求来了（CSS / JS），服务器还可以暂停当前流，先处理关键资源。

二进制分帧 ​

多路复用靠的是协议栈里多出来的 二进制分帧层：

  1. 浏览器准备好请求行、请求头，POST 再加请求体。
  2. 分帧层把它们切成带 stream ID 的二进制帧，交给 TCP 发出去。
  3. 服务器按 ID 把帧拼回一条完整请求，处理后再分帧发回。
  4. 浏览器同样按 ID 把帧交给对应请求。

语义没变：Accept、Cookie、缓存这些通信语言都还在，变的只是传输方式。所以现有生态不用推倒重来。

分帧层顺带带来的能力 ​

能力做什么
请求优先级发送时标优先级，服务器先处理重要请求
服务器推送用户要 HTML 时，顺手把即将用到的 CSS / JS 推过去，加快首屏
头部压缩页面常有上百个请求，多数只有头、没有体；把头压到原来的约 20%，收益很大

HTTP/2 规范 2015 年 5 月发布。用得好，传输效率大约能提升 20%～60%。

它解决的是 HTTP 层 队头阻塞。底层还是 TCP：丢一个包，这条连接上的所有流都会停。

HTTP/3：换掉 TCP ​

TCP 队头阻塞 ​

TCP 把数据拆成按序编号的包。中间丢一个，整条管道暂停，后面的包即使到了也要等重传。这叫 TCP 队头阻塞。

HTTP/2 多条请求挤在 同一条 TCP 上，丢一包会堵住这条连接里的所有请求。HTTP/1.1 反而有 6 条连接兜底：堵 1 条，另外 5 条还能传。有测试说丢包率到 2% 时，HTTP/1.1 甚至比 HTTP/2 更快。

mermaid
flowchart LR
    subgraph http2 [HTTP/2 一条 TCP]
        S1[stream 1]
        S2[stream 2]
        S3[stream 3]
        P[丢一个包]
        S1 --> P
        S2 --> P
        S3 --> P
        P --> All[所有流都停]
    end

握手太慢 ​

RTT：浏览器发包到服务器，再收回来，这一趟的时间。

HTTP/1、HTTP/2 都走 TCP；若再套 HTTPS，还要做 TLS 握手：

  1. TCP 三次握手，大约 1.5 个 RTT 之后才能发数据。
  2. TLS 1.2 / 1.3 再花 1～2 个 RTT。

数据出发前一共 3～4 个 RTT。机房近还好（约 30～40ms）；跨大陆一个 RTT 可能超过 100ms，握手就要 300～400ms，会明显觉得慢。

为什么不直接改 TCP ​

两条路都很难：

  1. 中间设备僵化。路由器、防火墙、NAT、交换机依赖很少升级的软件，大量吃 TCP 特性。客户端把 TCP 升级了，包经过这些设备可能直接被丢掉。
  2. 操作系统僵化。TCP 在内核里，应用只能用、不能改，内核更新又慢于应用。

另起一个全新传输协议也不行：中间设备只认 TCP 和 UDP。HTTP/3 的折中是 在 UDP 上做一套像 TCP 的能力，叫 QUIC。

mermaid
flowchart TB
    subgraph h2 [HTTP/2]
        A1[HTTP/2] --> A2[TLS] --> A3[TCP] --> A4[IP]
    end
    subgraph h3 [HTTP/3]
        B1[HTTP/3] --> B2[QUIC 含 TLS 1.3] --> B3[UDP] --> B4[IP]
    end

QUIC 补了什么 ​

  • 可靠传输：UDP 本身不可靠，QUIC 补上重传、拥塞控制、流量控制。
  • 内置 TLS 1.3：握手 RTT 更少。
  • 真正独立的多路复用：同一条物理连接上多条逻辑流互不影响。丢一包只堵那一条流，其他流继续走，这才拆掉 TCP 队头阻塞。
  • 0-RTT / 1-RTT 建连：基于 UDP，可以尽快收发，对首次打开页面更友好。

可以把它看成「TCP 的可靠传输 + HTTP/2 的多路复用 + TLS」打成一套，从传输层把 Web 文件传输重做了一遍。

落地并不轻松 ​

动的是底层协议，推广会比 HTTP/2 慢：

  1. 早期浏览器、服务器支持不完整（Chrome 很早就有 Google 版 QUIC，和后来的标准 QUIC 差很多）。
  2. 内核对 UDP 的优化远不如 TCP。
  3. 中间设备对 UDP 更差，当时统计走 QUIC 大约有 3%～7% 的丢包。

常见状态码 ​

  • 200 成功。
  • 301 永久重定向，后续应改用新 URL。
  • 302 临时重定向。
  • 304 协商缓存命中，资源未改，用本地副本。
  • 401 未认证，服务器不知道你是谁。
  • 403 已识别身份，但没有权限。
  • 404 资源不存在。
  • 405 方法不被允许。
  • 406 无法按客户端要求的内容特性返回。
  • 408 请求超时。
  • 413 请求体太大。
  • 500 服务器内部错误。
  • 502 网关从上游拿到了无效响应。
  • 503 服务暂时不可用（过载或维护）。
  • 504 网关等上游超时。
