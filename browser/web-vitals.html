前端性能优化指标（Web Vitals） ​

前端性能不只是「感觉快不快」，而是可以用一套标准指标量化：页面多久能看见内容、多久能交互、过程中会不会抖。Google 把其中与用户体验最相关的指标归为 Core Web Vitals（核心网页指标），并影响搜索体验评估；Lighthouse、Chrome UX Report（CrUX）、Performance 面板也会围绕它们打分。

本文按页面加载时间线串起各指标，并区分加载过程与交互过程两类问题：先讲清定义与阈值，再给对应优化手段和可落地示例，最后补测量监控与面试追问。

1. 为什么要关注这些指标 ​

视角意义
用户体验首屏白屏久、点击无响应、布局乱跳，会直接带来跳出与投诉
业务电商/内容站的转化率、广告曝光与加载速度强相关
SEOCore Web Vitals 是 Google 页面体验信号的一部分
工程把「优化」从拍脑袋变成可度量、可回归的目标

Core Web Vitals 当前三项（分别对应三类体验）：

  • LCP（Largest Contentful Paint，最大内容绘制）：加载体验——主要内容何时画完
  • INP（Interaction to Next Paint，交互到下一帧绘制）：交互响应（已替代 FID / First Input Delay）
  • CLS（Cumulative Layout Shift，累计布局偏移）：视觉稳定性——加载插入与交互弹层都可能贡献，不独占某一阶段

FCP（First Contentful Paint）、TTFB（Time to First Byte）、TBT（Total Blocking Time）、SI（Speed Index）等虽不一定是「核心三项」，但排查问题和读 Lighthouse 报告时几乎天天碰到，下文一并讲细。

2. 指标全景与时间线 ​

一次导航从用户按下回车到页面「可用」，大致时间线如下（上半段偏加载，下半段偏交互/稳定）：

text
导航开始
  │
  │  ========== 加载过程（何时能看见、内容是否就绪）==========
  ├─ DNS / TCP / TLS
  ├─ 首字节到达 ─────────────── TTFB (Time to First Byte)
  ├─ 首次绘制像素 ───────────── FP (First Paint)
  ├─ 首次内容绘制 ───────────── FCP (First Contentful Paint)
  ├─ 最大内容绘制 ───────────── LCP (Largest Contentful Paint)   ← Core Web Vital
  ├─ DOM 解析完成 ───────────── DOMContentLoaded (DCL)
  ├─ 资源与依赖加载完 ───────── Load (load event)
  ├─ 可视填充速度 / 主线程阻塞 ─ SI (Speed Index) / TBT (Total Blocking Time)
  │
  │  ========== 交互过程（点了是否立刻有反馈）==========
  ├─ 用户点击 / 触控 / 键盘 ─── INP (Interaction to Next Paint)   ← Core Web Vital
  │
  │  ========== 跨阶段（加载与交互都可能发生）==========
  └─ 意外布局偏移累计 ───────── CLS (Cumulative Layout Shift)   ← Core Web Vital

2.1 加载过程 vs 交互过程 ​

不要把「首屏慢」和「点击卡」当成同一类问题，指标和优化手段都不同：

阶段用户感知主要指标优化重心
加载过程多久能看见、主要内容何时就绪TTFB、FP、FCP、LCP、DCL、Load、SI；TBT 常反映首屏主线程是否被堵CDN/SSR、关键资源优先级、图片与字体、减同步 JS
交互过程点了/输入后多久有下一帧反馈INP（现场）；TBT 大时交互也容易差拆长任务、事件回调要短、减 hydration、延后第三方
跨阶段：稳定性页面会不会突然抖一下CLS媒体占位、广告位预留、字体策略；加载插内容与交互弹层都要管

对应关系（面试也好讲）：

  • Core Web Vitals 里：LCP 偏加载，INP 偏交互，CLS 管稳定（两阶段都可能扣分）
  • 实验室里 TBT/SI 多用来诊断加载期主线程与视觉进度；线上交互体验以 INP 为准

2.2 一览表（阈值以实验室/官方常用为准） ​

3. TTFB（Time to First Byte）—— 首字节时间 ​

3.1 定义 ​

TTFB（Time to First Byte，首字节时间）：从浏览器发起请求到接收到响应第一个字节的时间。它反映：

  • DNS / 建连 / TLS 握手开销
  • 服务器处理耗时（SSR、网关、DB）
  • 到用户的网络 RTT

TTFB 本身不是 Core Web Vital，但 TTFB 慢会拖垮 FCP/LCP。

3.2 怎么测 ​

js
// Navigation Timing Level 2
new PerformanceObserver((list) => {
  const nav = list.getEntries()[0]
  // responseStart - requestStart ≈ 等待首字节
  const ttfb = nav.responseStart - nav.requestStart
  console.log('TTFB(ms):', ttfb)
}).observe({ type: 'navigation', buffered: true })

DevTools → Network → 文档请求的 Timing：Waiting (TTFB)。

3.3 优化手段 ​

  1. 边缘/CDN：静态 HTML、SSR 结果尽量就近返回；开启 HTTP/2 或 HTTP/3。
  2. 服务端提速：接口并行、缓存热点、减少 SSR 串行 await；Node/SSR 注意冷启动。
  3. 缓存：HTML 合理用 Cache-Control / CDN 缓存；API 用短缓存或 stale-while-revalidate。
  4. 减少重定向：一次 301/302 往往多一整次 RTT。
  5. 连接复用：预连接关键源：
html
<link rel="preconnect" href="https://api.example.com" crossorigin />
<link rel="dns-prefetch" href="https://cdn.example.com" />
  1. Early Hints / 103：在真正响应前先推关键 CSS/字体提示（需 CDN/服务器支持）。

Checklist

  • [ ] HTML 是否被不必要地动态渲染、且无缓存
  • [ ] 是否存在跨机房、跨运营商的超长链路
  • [ ] 是否有链式重定向（http→https→www→业务域）

4. FP（First Paint）/ FCP（First Contentful Paint）—— 首次绘制与首次内容绘制 ​

4.1 定义 ​

指标全称含义
FPFirst Paint（首次绘制）浏览器第一次向屏幕画了任意像素（背景色也算）
FCPFirst Contentful Paint（首次内容绘制）第一次绘制了「内容」：文本、图片（含背景图）、非白色 canvas、SVG 等

用户感知上：FCP（First Contentful Paint）更有意义——说明「不是纯白屏了」。FCP 快不代表主要内容就绪（那是 LCP / Largest Contentful Paint）。

4.2 触发与注意点 ​

  • 只有绘制到用户可见内容才算 FCP；opacity: 0、visibility: hidden 等不可见内容通常不算。
  • iframe 内的内容不计入父页面 FCP。
  • SPA 若首屏 HTML 几乎为空、全靠 JS 渲染，FCP 会明显偏晚。

4.3 怎么测 ​

js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.name === 'first-contentful-paint') {
      console.log('FCP:', entry.startTime)
    }
  }
}).observe({ type: 'paint', buffered: true })

// 或
performance.getEntriesByName('first-contentful-paint')[0]?.startTime

4.4 优化手段 ​

  1. 尽快出 HTML 骨架：SSR / SSG / 流式 SSR，避免「空壳 HTML + 巨型 JS」。
  2. 关键 CSS 别阻塞太久：首屏 CSS 内联或拆出 critical CSS；非首屏样式异步。
  3. 去掉渲染路径上的同步脚本：<script> 无 defer/async 会阻塞解析（详见 6.4 defer 与 async）。
  4. 字体：避免长时间不可见文本（FOIT）；使用 font-display: swap，并 preload 关键字体。
  5. 减少关键请求链：HTML → CSS → 字体 → 文本，链路越长 FCP 越晚。
html
<link rel="preload" href="/fonts/brand.woff2" as="font" type="font/woff2" crossorigin />
<style>
  @font-face {
    font-family: Brand;
    src: url('/fonts/brand.woff2') format('woff2');
    font-display: swap;
  }
</style>

FCP vs LCP（面试常问）

  • FCP（First Contentful Paint）：第一次「有内容」
  • LCP（Largest Contentful Paint）：视口内「最大那块内容」画完
  • 优化 FCP ≠ 优化 LCP：例如很快画出导航栏文字（FCP 好），但 Hero 大图很晚（LCP 差）

5. LCP（Largest Contentful Paint）—— 最大内容绘制（Core Web Vital） ​

5.1 定义 ​

LCP（Largest Contentful Paint，最大内容绘制） 记录视口内最大内容元素完成绘制的时间点。加载过程中「当前最大元素」可能变化，最终取最后一个候选元素的绘制时间。

常见 LCP 元素类型：

  • <img>、<image>（SVG 内）
  • <video> 的海报图（poster）
  • 通过 url() 加载的背景图对应的元素
  • 包含文本节点的块级元素（如标题、段落所在块）

5.2 阈值 ​

  • 良好：≤ 2.5s
  • 需改进：2.5s – 4s
  • 差：> 4s

5.3 怎么测 ​

js
new PerformanceObserver((list) => {
  const entries = list.getEntries()
  const last = entries[entries.length - 1]
  console.log('LCP element:', last.element, 'time:', last.startTime)
}).observe({ type: 'largest-contentful-paint', buffered: true })

Chrome Performance / Lighthouse 的 LCP 会标出具体元素。也可使用官方库：

bash
npm i web-vitals
js
import { onLCP } from 'web-vitals'
onLCP(console.log)

5.4 LCP 变慢的四段拆解 ​

官方常把 LCP 拆成：

  1. TTFB
  2. 资源加载延迟（发现资源太晚：没 preload、被 JS 才插入）
  3. 资源加载耗时（体积大、带宽差、未压缩）
  4. 元素渲染延迟（资源已到，但被长任务/主线程忙卡住才画）

对症下药比「整体再压一点包」有效得多。

5.5 优化手段（详细） ​

（1）让 LCP 资源尽早被发现 ​

html
<!-- Hero 图：尽早声明，避免等 JS 水合后再插 img -->
<img
  src="/hero.avif"
  alt="..."
  width="1200"
  height="600"
  fetchpriority="high"
/>

<!-- 若 LCP 是 CSS 背景图，改用 <img> 或 preload -->
<link rel="preload" as="image" href="/hero.avif" fetchpriority="high" />
  • 不要把 LCP 图放在客户端路由懒加载组件里「首屏才 mount」。
  • 轮播图：首帧图用原生 <img>，其余再懒加载。

（2）减小与加速 LCP 资源 ​

  • 现代格式：AVIF / WebP，按设备输出合适尺寸（srcset + sizes）
  • CDN + HTTP 缓存；开启压缩（Brotli）
  • 避免超大原图当 Hero
html
<img
  src="/hero-800.avif"
  srcset="/hero-800.avif 800w, /hero-1200.avif 1200w, /hero-1600.avif 1600w"
  sizes="(max-width: 768px) 100vw, 1200px"
  width="1200"
  height="600"
  alt="hero"
  fetchpriority="high"
/>

（3）减少渲染阻塞 ​

  • 关键 CSS 体积控制；非关键 CSS media 或异步加载
  • 大包 JS defer；首屏不要同步执行超重 hydration
  • 考虑流式 SSR / 选择性水合，让 HTML 文本型 LCP 更早出现

（4）若 LCP 是文本 ​

  • 系统字体或已 preload 的 Web 字体
  • 避免用 JS 晚到的 CSS 才给标题设置可见样式

Checklist

  • [ ] 用 Performance 确认当前 LCP 元素是谁
  • [ ] 该资源是否在 HTML 早期即可发现（而非 JS 注入）
  • [ ] 是否设置了 fetchpriority="high" / preload
  • [ ] 是否与大量低优先级请求抢带宽

6. DOMContentLoaded（DCL）与 Load（load event） ​

6.1 定义 ​

事件/时机全称含义
DCLDOMContentLoadedHTML 解析完成，DOM 就绪；不等待样式表、图片、子帧（但同步脚本会推迟）
Loadload event（窗口 load 事件）页面依赖的资源（图片、样式表等）都加载完成

它们是传统 Timing API 指标，不是 Core Web Vitals，但 Network 面板、老监控系统仍大量使用。

js
performance.timing.domContentLoadedEventEnd - performance.timing.navigationStart // 旧 API
// 推荐：
const [nav] = performance.getEntriesByType('navigation')
nav.domContentLoadedEventEnd
nav.loadEventEnd

6.2 和 FCP/LCP 的关系 ​

  • DCL 早 ≠ 用户看见内容早（可能 CSS 还在挡）
  • Load 晚很常见（一堆非关键图），不要用 Load 当唯一性能 KPI
  • 现代优化目标应转向 LCP / INP / CLS，DCL/Load 作辅助诊断

6.3 优化思路 ​

  • 脚本加 defer，减少对 HTML 解析的阻塞 → DCL 更合理
  • 图片懒加载、第三方脚本延后 → Load 不再被拖死，但不牺牲 LCP 图
  • 监控上可同时报：LCP + domContentLoaded + load，避免只盯 Load

6.4 defer 与 async 的区别 ​

普通 <script src="...">（无属性）会阻塞 HTML 解析：遇到标签就停下来下载并立刻执行，执行完才继续解析后面的 DOM。这会推迟 FCP/LCP，也会推迟 DCL。

defer 和 async 都让脚本并行下载、不阻塞解析，差别在何时执行、是否保序。

对比一览 ​

普通 scriptasyncdefer
下载时是否阻塞 HTML 解析是（下载+执行都挡着）否否
执行时机下载完立刻执行下载完立刻执行（可能插在解析中途）HTML 解析完成后、DOMContentLoaded 之前
多个脚本执行顺序文档顺序不保证（谁先下完谁先跑）保证按文档顺序
是否会推迟 DCL会（阻塞解析）可能（执行若撞上解析/DCL 前后）会等 defer 脚本执行完再触发 DCL
典型用途必须立刻改 DOM 的极少数场景独立第三方：统计、广告、无依赖脚本主业务包、有依赖关系的多个脚本
text
时间线示意（简化）：

普通 script:
  解析 HTML → [卡住：下载+执行 script] → 继续解析 → DCL

async:
  解析 HTML ──────────────→ DCL
       └─ 并行下载 script ─┘
            下载完就执行（可能打断解析，执行顺序看网速）

defer:
  解析 HTML ──────────────→ 按序执行所有 defer → DCL
       └─ 并行下载 script ─┘

代码示例 ​

html
<!-- 阻塞解析：能不用就不用（或放到 </body> 前仍不如 defer 清晰） -->
<script src="/sync.js"></script>

<!-- async：互不依赖的第三方 -->
<script async src="https://www.googletagmanager.com/gtag/js"></script>

<!-- defer：自家应用入口，多文件时保序 -->
<script defer src="/vendor.js"></script>
<script defer src="/app.js"></script>
html
<!-- type="module" 默认就是 defer 语义（延迟执行、保序） -->
<script type="module" src="/main.js"></script>
<!-- module 若加 async，则不再等文档解析完，下完就执行，且不保序 -->
<script type="module" async src="/widget.js"></script>

怎么选（结合性能指标） ​

  1. 首屏业务 JS（有依赖、要操作完整 DOM）→ defer
    不挡解析，执行时 DOM 已就绪，顺序可控，有利于 FCP/LCP；DCL 会等 defer 跑完，这是预期行为。
  2. 无依赖的埋点/广告 → async
    尽早执行、不拖业务；注意它可能在 DOM 未就绪时跑，脚本内部要自己判断，且可能和解析抢主线程，间接影响 INP/TBT。
  3. 既要早又有依赖 → 不要用多个 async 硬拼顺序
    用 defer、打包成一个入口，或 type="module" + import。
  4. 动态 import() / 路由懒加载
    与标签属性无关，属于运行时再拉代码，适合非首屏，减轻首屏 TBT/INP。

常见误区 ​

  • 「async 比 defer 更快所以业务包也用 async」——业务多文件会乱序，且可能在 DOM 未完成时执行报错。
  • 「脚本放在 </body> 前就不用 defer」——仍可能阻塞解析尾部；defer 语义更明确，还可放在 <head> 提前开下。
  • 「defer 不推迟 DCL」——错：规范要求 defer 脚本在 DCL 前执行完，DCL 会等它们。

7. CLS（Cumulative Layout Shift）—— 累计布局偏移（Core Web Vital） ​

7.1 定义 ​

CLS（Cumulative Layout Shift，累计布局偏移） 衡量页面生命周期内意外布局偏移的严重程度。元素在用户非预期情况下发生位移，会贡献分数。

CLS 跨加载与交互两阶段：首屏图片/广告晚到把内容顶下去，和点击后弹出未占位的条幅，都会记入 CLS。优化时两边都要查，不能只盯「加载」或只盯「点击」。

单次偏移分数近似：

[ \text{Layout Shift Score} = \text{impact fraction} \times \text{distance fraction} ]

  • impact fraction：不稳定元素影响的视口比例
  • distance fraction：移动距离占视口的比例

CLS（Cumulative Layout Shift） 是会话窗口内这些分数的累计（Chrome 使用 session window 算法，避免无限累加）。

7.2 阈值 ​

  • 良好：≤ 0.1
  • 需改进：0.1 – 0.25
  • 差：> 0.25

7.3 什么算 / 不算 ​

  • 用户交互后 500ms 内的偏移通常可豁免（预期内变化）
  • 图片、广告、字体、动态插入 DOM 导致下方内容「被顶下去」——典型扣分项

7.4 怎么测 ​

js
let cls = 0
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) {
      cls += entry.value
      console.log('CLS +=', entry.value, 'total:', cls, entry.sources)
    }
  }
}).observe({ type: 'layout-shift', buffered: true })
js
import { onCLS } from 'web-vitals'
onCLS(console.log)

7.5 优化手段（详细） ​

（1）媒体预留尺寸 ​

html
<!-- 一定要带宽高，或用 CSS aspect-ratio -->
<img src="a.jpg" width="800" height="450" alt="" />

<style>
  .cover {
    width: 100%;
    aspect-ratio: 16 / 9;
    height: auto;
  }
</style>

（2）广告 / 嵌入位先占位 ​

css
.ad-slot {
  min-height: 250px; /* 与实际广告尺寸一致 */
}

（3）字体引起的偏移（FOUT/FOIT） ​

  • font-display: optional 或 swap + 接近的 fallback 度量（size-adjust / ascent-override 等）
  • preload 关键字体，减少「先系统字体后 Web 字体」的跳动

（4）动态内容插入位置 ​

  • 骨架屏尺寸与最终内容一致
  • 避免在已有内容上方插入横幅；改到底部或预留顶栏高度
  • 动画优先用 transform / opacity，避免改 top/height 带动文档流

（5）不要用会撑开布局的晚到 CSS ​

关键布局信息应在首屏 CSS 中；避免 JS 运行后才注入改变盒模型的样式。

Checklist

  • [ ] 所有 img/video/iframe 是否有尺寸或 aspect-ratio
  • [ ] 顶栏公告、Cookie 条是否预留高度
  • [ ] Web 字体切换是否导致标题行高剧变
  • [ ] 无限列表/插入节点是否在视口上方插入

8. INP（Interaction to Next Paint）—— 交互到下一帧绘制（Core Web Vital） ​

8.1 定义 ​

INP（Interaction to Next Paint，交互到下一帧绘制） 观察用户与页面交互（点击、触控、键盘）到浏览器完成下一帧绘制的延迟，取页面生命周期中的高百分位表现（近似「最差的一批交互」）。

一次交互延迟大致包含：

  1. 输入延迟：等到主线程空闲才能处理事件
  2. 处理时间：事件回调执行时长
  3. 展示延迟：样式/布局/绘制到下一帧

2024 起 INP 正式替代 FID 成为 Core Web Vital。FID 只量「第一次输入」的输入延迟，覆盖面远小于 INP。

8.2 阈值 ​

  • 良好：≤ 200ms
  • 需改进：200ms – 500ms
  • 差：> 500ms

8.3 怎么测 ​

js
import { onINP } from 'web-vitals'
onINP(console.log) // 需真实用户交互才会有值

实验室可用 Performance 面板看长任务、Interaction 轨道；Lighthouse 对 INP 的实验室模拟有限，更依赖 RUM 现场数据。

8.4 优化手段（详细） ​

（1）拆长任务，让输入能插队 ​

主线程连续执行 > 50ms 的任务会拖垮 INP。

js
// 大数组处理：让出主线程
async function processInChunks(items, chunkSize = 100) {
  for (let i = 0; i < items.length; i += chunkSize) {
    const chunk = items.slice(i, i + chunkSize)
    // 重计算...
    await new Promise((r) => setTimeout(r, 0))
    // 或 scheduler.yield?.()
  }
}
  • 使用 requestIdleCallback / scheduler.postTask 安排非紧急工作
  • 代码分割，减少首屏 hydration 体积（React/Vue 选择性水合、懒加载非首屏组件）

（2）事件处理要短 ​

js
button.addEventListener('click', (e) => {
  // 先做最少的 UI 反馈
  button.disabled = true
  button.textContent = '提交中...'

  // 重活放到宏任务/ Worker
  queueMicrotask(() => {}) // 微任务仍占主线程，重活别全塞这里
  setTimeout(() => heavyCompute(), 0)
})
  • 避免在 input/scroll 里做强制同步布局（先读后写混用导致 layout thrashing）
  • 列表用虚拟滚动，减少一次交互引发的巨量 DOM 更新

（3）尽快画出下一帧 ​

  • 用 CSS transform/opacity 做动画，走合成线程
  • 避免交互里同步查询 offsetHeight 又立刻改样式
  • 大列表更新可 startTransition（React）等降低优先级，保证输入响应

（4）第三方脚本 ​

统计、客服、广告脚本常占用主线程：延迟加载、facade 模式（点击再加载）、严格 CSP 与标签管理。

INP vs FID（First Input Delay，首次输入延迟）

FID（First Input Delay）INP（Interaction to Next Paint）
范围仅首次输入的等待时间整个页面多种交互到下一帧
是否含处理与绘制基本不含处理耗时含处理与展示
现状已退出 Core Web Vitals当前标准

9. TBT（Total Blocking Time）—— 总阻塞时间 ​

9.1 定义 ​

TBT（Total Blocking Time，总阻塞时间）：在 FCP 到 TTI（Time to Interactive，可交互时间）相关窗口内，所有长任务超出 50ms 部分的阻塞时间总和。

例如一个 120ms 的任务，贡献阻塞 = 120 - 50 = 70ms。多个长任务累加。

TBT 是实验室指标，和现场的 INP 高度相关：TBT 大，主线程常忙，交互易卡。

9.2 阈值（Lighthouse 常用） ​

  • 良好：≤ 200ms
  • 需改进：200ms – 600ms
  • 差：> 600ms

9.3 优化手段 ​

与 INP 高度重合：

  1. 减小主线程 JS：tree-shaking、拆包、去掉无用 polyfill
  2. 拆长任务（yield）
  3. 延后非关键第三方
  4. Web Worker 做计算密集任务
  5. 避免巨型同步 JSON.parse / 模板编译堵在首屏

Performance 面板 → Bottom-Up / Main → 找红色长任务条，是优化 TBT 的第一步。

10. SI（Speed Index）—— 速度指数 ​

10.1 定义 ​

SI（Speed Index，速度指数） 衡量页面可视区域内容填充的速度：不是某一个时刻，而是「画面多快走完」的整体指数。数值越低越好。

Lighthouse 通过拍摄加载过程中的视觉进度计算。它能发现「FCP 还行但长时间停留在骨架/残缺 UI」的问题。

10.2 优化手段 ​

  • 提升 FCP/LCP 的同时，让首屏关键区域更快完整呈现
  • 骨架屏接近真实布局，避免长时间大片空白
  • 优先加载视口内资源，视口外懒加载
  • 减少渲染阻塞 CSS/JS，避免「很晚才突然整页出现」

SI 适合作为 Lighthouse 对照指标，业务 KPI 仍建议以 LCP/INP/CLS 为主。

13. 面试高频追问 ​

Q1：FCP 和 LCP 区别？
FCP（First Contentful Paint）是第一次绘制内容；LCP（Largest Contentful Paint）是视口内最大内容绘制完成。FCP 好、LCP 差很常见（导航先出来，Hero 很晚）。

Q2：CLS 常见原因？
CLS（Cumulative Layout Shift）常见原因：无尺寸图片、晚到的 Web 字体、动态插入顶栏/广告、动画改动文档流属性。

Q3：为什么 FID 被 INP 替换？
FID（First Input Delay）只覆盖首次输入延迟，忽略处理耗时与后续交互；INP（Interaction to Next Paint）更贴近整页交互体验。

Q4：如何定位 LCP 元素？
Performance 面板 LCP 标记、PerformanceObserver 的 largest-contentful-paint、web-vitals 的 entries。

Q5：优化了 webpack 体积，LCP 为何还差？
LCP 可能是图片/接口 HTML，与 JS 包体积无关；应按 TTFB → 资源发现 → 下载 → 渲染延迟四段拆。

Q6：defer 和 async 的区别？对性能指标有何影响？
二者下载时都不阻塞 HTML 解析。defer 保序，在解析完成后、DOMContentLoaded 前执行，适合有依赖的业务包；async 下完就执行、不保序，适合独立第三方脚本，但可能打断解析并与主线程抢时间。详见上文 6.4 defer 与 async 的区别。首屏关键脚本优先 defer 或 type="module"。

Q7：强缓存能优化哪些指标？
重复访问的 TTFB/FCP/LCP 都会受益；首次访问还要靠 CDN、SSR、资源优先级等。

14. 小结 ​

  1. 先分阶段再看指标：加载看 LCP（辅 FCP / TTFB / SI），交互看 INP，稳定看 CLS（加载插入与交互弹层都可能扣分）；TBT 多用于加载期主线程诊断，差时交互也容易差。
  2. 核心三项：LCP（Largest Contentful Paint）、INP（Interaction to Next Paint）、CLS（Cumulative Layout Shift）；FCP / TTFB / TBT / SI 用于诊断与 Lab 对照。
  3. 按时间线理解：TTFB → FP / FCP → LCP → DCL / Load（加载），之后用户操作看 INP（交互），全程留意 CLS。
  4. 优化要对症：先确认是加载慢还是交互卡，再用工具定位「哪个指标、哪个元素/哪段耗时」。
  5. Lab + Field 双轨：本地 Lighthouse 回归，线上 p75 才是是否达标的依据。
