React 性能优化 ​

随着应用复杂度上升，性能优化往往决定用户体验。下面按「减少无效渲染 → 并发调度 → 结构与列表 → 定位手段」梳理常用策略。

常用优化技巧 ​

PureComponent 与 shouldComponentUpdate ​

在 shouldComponentUpdate 里可以手动对比新旧 props / state，决定是否继续渲染。PureComponent 则自动做浅比较，减少无效更新。

jsx
class MyComponent1 extends React.PureComponent {
  render() {
    return <div>{this.props.name}</div>
  }
}

class MyComponent2 extends React.Component {
  shouldComponentUpdate(nextProps) {
    return this.props.someImportantProp !== nextProps.someImportantProp
  }

  render() {
    return null
  }
}

React.memo ​

React.memo 是函数组件侧的高阶组件，默认用 Object.is 比较每个 prop；可通过第二个参数自定义比较逻辑。

合理拆分组件：把「常变」和「不常变」拆开，对不依赖父级频繁变化 props 的叶子节点包一层 memo。

jsx
function arePropsEqual(oldProps, newProps) {
  return (
    oldProps.dataPoints.length === newProps.dataPoints.length &&
    oldProps.dataPoints.every((oldPoint, index) => {
      const newPoint = newProps.dataPoints[index]
      return oldPoint.x === newPoint.x && oldPoint.y === newPoint.y
    })
  )
}

const MyComponent = React.memo(function MyComponent(props) {
  /* 使用 props 渲染 */
}, arePropsEqual)

使用 PureComponent / memo 时的坑 ​

二者都是浅比较。父组件每次渲染若给子组件传入新的函数 / 对象引用，子组件仍会误更新，优化等于没做。

函数组件里，内联箭头函数、匿名函数，以及在组件体内声明的普通函数，每次渲染都是新引用：

jsx
export default function Father1() {
  const [name, setName] = React.useState('')
  const [value, setValue] = React.useState('')

  // 每次 Father1 渲染，setData 都是新引用
  const setData = (v) => {
    setValue(v)
  }

  return (
    <div>
      <button onClick={() => setName('父组件的数据' + Math.random())}>
        点击刷新父组件
      </button>
      {name}
      <Children1 callback={setData} />
    </div>
  )
}

class Children1 extends React.PureComponent {
  render() {
    return <div>这里是子组件</div>
  }
}

class 组件里在 render 中写箭头函数 / bind，同样会制造新引用：

jsx
// ❌ 每次 render 都是新函数
<Children1 callback={() => this.setState({ count: 11 })} />
<Children1 callback={this.setCount.bind(this, '11111')} />

正确做法：把方法绑到实例上（constructor 里 bind，或类字段箭头函数），再把函数引用传给子组件：

jsx
export default class Father extends React.Component {
  state = { name: '', count: '' }

  setCount = (count) => {
    this.setState({ count })
  }

  render() {
    return (
      <div>
        <button
          onClick={() =>
            this.setState({ name: '父组件的数据' + Math.random() })
          }
        >
          点击获取数据
        </button>
        {this.state.name}
        <Children1 callback={this.setCount} />
      </div>
    )
  }
}

思考：是不是到处都该加 memo？ ​

不是。React 文档的态度是：

只有当你的组件经常用完全相同的 props 重渲染，且这次渲染本身很贵时，memo 才值得。若重渲染没有可感知延迟，就不必。若 props 每次都不同（渲染期间新建对象 / 函数），memo 几乎没用——这也是为什么常要配合 useMemo / useCallback。

useMemo、useCallback：稳定 Props / 缓存计算结果 ​

传给子组件的派生值或函数若每次都是新引用，PureComponent / memo 会失效，这时用 useMemo / useCallback 稳住引用。

jsx
import { useState, useMemo, useCallback, memo } from 'react'

const Children1 = memo(function Children1({ callback }) {
  return <button onClick={() => callback('ok')}>子组件</button>
})

function App() {
  const [count, setCount] = useState(0)
  const [value, setValue] = useState('')

  const memoizedValue = useMemo(() => {
    const list = new Array(1000).fill(null).map((_, i) => i)
    const total = list.reduce((res, cur) => res + cur, 0)
    return count + total
  }, [count])

  // 稳定函数引用，配合 memo / PureComponent 子组件
  const setData = useCallback((v) => {
    setValue(v)
  }, [])

  return (
    <div>
      {memoizedValue}
      {value}
      <button onClick={() => setCount((prev) => prev + 1)}>按钮</button>
      <Children1 callback={setData} />
    </div>
  )
}

是不是到处都该加 useMemo / useCallback？ ​

不必。它们主要在重渲染路径上有价值；首次渲染时反而可能多做一些工作，并增加依赖声明与心智负担。优先在「已确认昂贵」或「需要稳定引用喂给 memo 子组件」的地方使用。

用 useMemo 缓存「子树 JSX」 ​

useMemo 返回的是元素时，依赖不变可跳过该子树的 Render，效果类似 memo，但更局部、不必再包一层组件：

jsx
import { useEffect, useMemo, useState } from 'react'

const renderCntMap = {}

function Comp({ name }) {
  renderCntMap[name] = (renderCntMap[name] || 0) + 1
  return (
    <div>
      组件「{name}」 Render 次数：{renderCntMap[name]}
    </div>
  )
}

export default function App() {
  const setCnt = useState(0)[1]

  useEffect(() => {
    const timer = window.setInterval(() => {
      setCnt((v) => v + 1)
    }, 1000)
    return () => clearInterval(timer)
  }, [setCnt])

  const comp = useMemo(() => {
    return <Comp name="使用 useMemo 作为 children" />
  }, [])

  return (
    <div>
      <Comp name="直接作为 children" />
      {comp}
    </div>
  )
}

useTransition ​

用 startTransition 把一次更新标成非紧急：可被打断，优先保证更重要的交互（如输入、点击反馈）。

典型场景：多 Tab，其中一个渲染很重，快速切换会卡：

jsx
import { useState, memo, useTransition } from 'react'

function TabButton({ isActive, onClick, children }) {
  return (
    <button onClick={onClick} style={{ fontWeight: isActive ? 'bold' : 'normal' }}>
      {children}
    </button>
  )
}

function SlowPost({ index }) {
  const start = performance.now()
  while (performance.now() - start < 1) {}
  return <li>Post #{index + 1}</li>
}

function AboutTab() {
  return <p>About</p>
}

const PostsTab = memo(function PostsTab() {
  const items = []
  for (let i = 0; i < 500; i++) {
    items.push(<SlowPost key={i} index={i} />)
  }
  return <ul>{items}</ul>
})

export default function TabContainer() {
  const [tab, setTab] = useState('about')
  const [isPending, startTransition] = useTransition()

  function selectTab(nextTab) {
    startTransition(() => {
      setTab(nextTab)
    })
  }

  return (
    <div>
      <div style={{ opacity: isPending ? 0.7 : 1 }}>
        <TabButton
          isActive={tab === 'about'}
          onClick={() => selectTab('about')}
        >
          About
        </TabButton>
        <TabButton
          isActive={tab === 'posts'}
          onClick={() => selectTab('posts')}
        >
          Posts (slow)
        </TabButton>
      </div>
      {tab === 'about' && <AboutTab />}
      {tab === 'posts' && <PostsTab />}
    </div>
  )
}

isPending 可用于切换期间的 loading / 降透明度提示。

useDeferredValue ​

延迟「不紧急」的派生值，类似「保留最新一次、中间可被打断」的效果，适合输入框实时响应 + 下方大列表按延迟值过滤。

jsx
import { useState, useDeferredValue, memo } from 'react'

export default function App() {
  const [text, setText] = useState('')
  const deferredText = useDeferredValue(text)

  return (
    <>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <SlowList text={deferredText} />
    </>
  )
}

const SlowList = memo(function SlowList({ text }) {
  const arr = []
  for (let i = 0; i < 200; i++) {
    let startTime = performance.now()
    while (performance.now() - startTime < 1) {}
    if (String(i).includes(text)) {
      arr.push(<li key={i}>{i}</li>)
    }
  }
  return <ul>{arr}</ul>
})

useTransition 控制的是「你主动触发的那次 setState」；useDeferredValue 控制的是「基于某个已变 value 的延后展示」。

Fragment ​

多元素并列且不需要真正容器时，用 Fragment（或 <>...</>）避免多包一层 DOM，有利于布局与语义；性能收益通常很小，别把它当成「加速魔法」。

jsx
const MyComponent = () => (
  <>
    <div>Element 1</div>
    <div>Element 2</div>
  </>
)

合理使用 Context ​

Context 能跨层传数据，但 value 一变，所有 useContext 订阅者都会更新，且会绕过你对「其它 props」做的 memo 期待——订阅了 Context 的组件仍会因 Context 变化而渲染。

常见缓解：

  1. 拆分读写：外层读 Context，把真正用到的字段作为 props 传给 memo 子组件。
  2. 拆 Context：把变化频率不同的字段拆成多个 Context（或拆 Provider）。
  3. 发布订阅 / 外部 store：中间层不传 props、不订阅 Context，只有真正关心数据的组件订阅（Redux、Zustand、MobX、useSyncExternalStore 等）。

更细的「谁会 re-render」见：useContext 更新谁 re-render。

状态下放，缩小影响范围 ​

状态只服务某棵子树时，把 state 下沉到该子树，避免拖着昂贵兄弟节点一起渲染。

jsx
// ❌ count 在 App，ExpensiveTree 跟着白跑
export default function App() {
  const [count, setCount] = useState(0)
  return (
    <div>
      <button onClick={() => setCount((c) => c + 1)} />
      <p>{count}</p>
      <ExpensiveTree />
    </div>
  )
}

// ✅ 状态下沉
export default function App() {
  return (
    <>
      <Form />
      <ExpensiveTree />
    </>
  )
}

若 DOM 结构要求「贵组件夹在中间」，可用 children / 插槽 把昂贵节点提到上层创建，再作为 props 传入：

jsx
export default function App() {
  return <ColorContainer expensiveTreeNode={<ExpensiveTree />} />
}

function ColorContainer({ expensiveTreeNode }) {
  const [count, setCount] = useState(0)
  return (
    <div>
      <button onClick={() => setCount((c) => c + 1)} />
      {expensiveTreeNode}
      <p>{count}</p>
    </div>
  )
}

这样 count 变化不会让 App / ExpensiveTree 再 Render。

列表 key ​

大型列表用稳定唯一的 key（通常业务 id），帮助 React 复用节点。

jsx
<ul>
  {items.map((item) => (
    <li key={item.id}>{item.name}</li>
  ))}
</ul>

补充：尽量避免用数组下标当 key（尤其是可插入 / 删除 / 排序的列表），否则容易复用错状态。

避免在提交阶段钩子里再 setState ​

componentDidMount / componentDidUpdate / componentWillUnmount、useLayoutEffect 发生在提交阶段（DOM 已更新、浏览器绘制前或同步路径上），会阻塞绘制。若在这里再 setState，等于立刻再跑一轮更新，耗时翻倍。能放到事件处理、数据请求回调里完成的，就不要塞进这些钩子。

useEffect 在绘制之后异步执行，一般不会直接卡首帧；但仍应避免「mount 后立刻又 setState 触发二次渲染」这类不必要的双渲染（除非确实依赖 DOM 测量等布局信息）。

虚拟化长列表 ​

超长列表只渲染可视区域，可用 react-window / @tanstack/react-virtual 等。

jsx
import { FixedSizeList as List } from 'react-window'

const Row = ({ index, style }) => <div style={style}>Item {index}</div>

const MyList = ({ items }) => (
  <List height={150} itemCount={items.length} itemSize={35} width={300}>
    {Row}
  </List>
)

动画尽量别绑死在 React 渲染上 ​

高频改样式若每帧都走 React setState，很容易掉帧。react-spring 等库用 rAF / Web Animations 直接改 DOM（或驱动非 React 状态），动画过程中不必整树重渲染。

不可变数据与浅比较（Immutable.js / Immer） ​

不可变更新能让「变没变」用引用 === 判断，从而让 shouldComponentUpdate / memo 更可靠。

两条常见路线：

  1. Immutable.js：用 Map / List 等专用结构，改数据必出新引用；API 学习成本较高，新项目已少用。
  2. Immer（更常见）：继续用普通 JS 对象，在 produce 里用「看起来像突变」的写法，库负责产出不可变的下一份状态。Redux Toolkit 默认内置 Immer。
js
import { produce } from 'immer'

const nextState = produce(state, (draft) => {
  draft.user.name = 'Tom'
  draft.list.push({ id: 3 })
})
// nextState 是新引用；未改动的子树尽量与旧 state 共享引用

也可用 React 自带的写法约定不突变（展开运算、map / filter 等）。不一定非要上库，有复杂嵌套更新时再考虑 Immer。

代码分割与懒加载 ​

jsx
import React, { lazy, Suspense } from 'react'

const LazyComponent = lazy(() => import('./LazyComponent'))

function App() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <LazyComponent />
    </Suspense>
  )
}

路由级、重型弹窗、低频功能块是最常见切分点。

其他通用手段 ​

  • Web Worker：重计算挪出主线程
  • SSR / 流式 SSR：优化首屏与 TTFB
  • 输入防抖 / 滚动节流
  • 图片、字体、包体积等资源侧优化（与 React 渲染正交，但体感影响很大）

性能定位工具 ​

React Profiler ​

内置 Profiler 可看提交耗时、更新原因；也可包一层 <Profiler> 拿回调数据。

jsx
import { Profiler } from 'react'

function onRenderCallback(
  id,
  phase,
  actualDuration,
  baseDuration,
  startTime,
  commitTime
) {
  console.log(`${id} ${phase} ${actualDuration}ms`)
}

function App() {
  return (
    <Profiler id="App" onRender={onRenderCallback}>
      {/* 组件树 */}
    </Profiler>
  )
}

注意：Profiler 收集的是提交阶段数据，定位不了「卡在 commit 之外」的问题（例如同步超长 JS、布局抖动）。

开发者工具里还可开启「记录组件更新原因」，对照是哪次 props / state / hooks 依赖触发了 Render。

补充：建议额外记住的几点 ​

点说明
先量再建用 Profiler / Performance 面板确认瓶颈，再上 memo；避免过早优化
React 18 自动批处理事件、Promise、超时器里的多次 setState 默认会批处理
Concurrent 选型交互优先 → startTransition；展示滞后于输入 → useDeferredValue
Context 拆分高频与低频 value 分开，比「一个大 Provider」更重要
React Compiler新项目可关注编译期自动 memo，减少手写 useMemo / useCallback 负担
key 与状态错误的 key 会导致「看起来像性能问题」的错误复用

小结 ​

性能优化的主线仍是：

  1. 少渲染：状态下沉、拆组件、memo + 稳定引用、Context / 列表虚拟化
  2. 巧调度：useTransition / useDeferredValue 保住交互流畅
  3. 晚加载：lazy + 路由 / 模块切分
  4. 先定位：Profiler 找到真瓶颈，再针对性动手
